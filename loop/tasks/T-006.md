# T-006 — Fix the same stale-entity lock defeat in HoldService.releaseHold
Milestone: M7 (#12)   Status: pending
Escalation: spawn `implementer` directly — this is a critical production concurrency defect
requiring the same Hibernate identity-map reasoning as T-003's fix, not a mechanical change.

## Description
T-003 found and fixed a production double-booking bug in `HoldService.spansMultipleEvents`:
an unlocked `findAllById` loaded managed `EventSeat` entities into the persistence context
before the locking loop, so Hibernate's identity map handed the later `findByIdForUpdate` the
stale pre-lock snapshot. The Postgres `SELECT ... FOR UPDATE` genuinely acquired the row lock;
the code then read data from before it.

**The identical pattern is still live in `HoldService.releaseHold`** (`HoldService.java:180-198`),
confirmed by code review:

```java
List<Long> seatIds = eventSeatRepository.findByCurrentHoldId(holdId).stream()  // 180: full managed entities, unlocked
        .map(EventSeat::getId).sorted().toList();

for (Long seatId : seatIds) {
    EventSeat eventSeat = eventSeatRepository.findByIdForUpdate(seatId)        // 186: same ids, same transaction
            .orElseThrow(...);
    Hold currentHold = eventSeat.getCurrentHold();
    if (currentHold != null && currentHold.getId().equals(holdId)) {           // 191: guard reads STALE value
        eventSeat.setStatus(EventSeatStatus.AVAILABLE);
        eventSeat.setCurrentHold(null);
    }
}
```

`findByCurrentHoldId` is a derived query rooted on `EventSeat`, so it returns fully-loaded
managed entities — not lazy proxies — for exactly the ids the loop then re-locks.

**Confirmed exploit:**
1. Thread A calls `releaseHold(H)`; its unlocked read returns seat 1 with `currentHold = H`.
2. Thread B runs `createHold` on seat 1, finds `H` lazily expired (ADR-0002), reconciles `H` to
   `EXPIRED`, reassigns seat 1 to a new hold `H2`, commits.
3. Thread A acquires the row lock. Postgres shows `H2`; Hibernate returns A's stale instance
   still showing `H`.
4. A's ownership guard passes against the stale value, so A sets the seat `AVAILABLE` and clears
   `currentHold` — **silently destroying B's valid, freshly-created hold**. B believes it holds a
   seat that is now free for anyone.

This needs no Redis outage — it is a plain create-vs-release timing race reachable in normal
production operation.

The comment at `HoldService.java:173-179` states precisely the invariant this violates: that the
read-check-write must happen under each seat's row lock "otherwise a concurrent createHold that
has already reassigned this seat to a brand-new hold (via lazy-expiry reconciliation, ADR-0002)
could be silently clobbered by this release." The intent is correct; the identity map defeats it.

**Not exploitable, already verified — do not change these:** `BookingService.createFromHold`
(line ~74) and `releaseBookingSeats` (line ~243) reach `EventSeat` only through
`@ManyToOne(fetch = LAZY)` associations on `HoldSeat`/`BookingSeat`. `getEventSeat()` returns an
uninitialized proxy and `.getId()` is served from its identifier field without initialization,
so no stale business state is cached, and both sites use the fresh instance from
`findByIdForUpdate` for all mutation. Review confirmed both are safe.

## Description of the fix
Unlike `spansMultipleEvents` — where a scalar projection cleanly removed the need for entities —
`releaseHold` genuinely wants the seat ids belonging to a hold. Choose deliberately between:
- **A scalar id projection** (`select es.id from EventSeat es where es.currentHold.id = :holdId`),
  mirroring T-003's fix. Nothing enters the persistence context. Likely the right answer, and
  consistent with the fix 60 lines above.
- **`entityManager.clear()` before the loop** — rejected in T-003 as a blunt instrument that also
  evicts unrelated entities; the same objection applies here, and more so, since the `Hold` was
  deliberately loaded and locked earlier in this method.

Whichever you choose, say why in a comment, and make sure the existing comment at lines 173-179
still tells the truth afterwards.

Note `findByCurrentHoldId` may have other callers — check before changing its signature; prefer
adding a projection method alongside it over changing it in place if anything else depends on it.

## Acceptance criteria
- The stale-read path is closed: after the fix, the ownership guard at line 191 reads the row as
  it exists *under the lock*.
- **A regression test that fails against the current code and passes after the fix.** This is the
  deliverable that proves the bug was real. Model it on T-003's
  `HoldRedisUnavailableRaceIntegrationTest` two-thread minimal repro: thread A releases hold `H`
  while thread B creates a new hold on one of `H`'s seats after forcing `H` past `expiresAt`.
  Assert B's hold survives and the seat is not left `AVAILABLE` with B believing it holds it.
  **Run the test against the unfixed code first and confirm it fails** — a regression test that
  passes before the fix proves nothing.
- No other `EventSeatRepository` read-then-lock call site is left unfixed. Review swept
  `service/`, `controller/`, `repository/` and found this as the only remaining instance
  (`HoldSweepService` uses a bulk `@Modifying` UPDATE; `EventSeatService` is read-only) — verify
  that sweep rather than trusting it.
- Full `./mvnw test` green, including all of T-001/T-002/T-003's suites.

## ADR
Write **ADR-0010** recording the general discipline, covering both this site and T-003's:
*never materialize a managed entity from an unlocked read, in the same transaction, for an id
that will later be read under `findByIdForUpdate`* — because Hibernate's identity map returns the
already-managed instance rather than refreshing it, so the row lock is acquired and its data
ignored. State it generally enough to be checkable against new code. It meets all three ADR
criteria: hard to reverse (a codebase-wide discipline now encoded in two non-obvious query
shapes), surprising (`findAllById` compiles, type-checks, reads naturally, and passes review by
skim), and a real trade-off (a projection is less convenient than the obvious entity query).
Reference both call sites so a future contributor "simplifying" either one finds the reason.

## Relevant conventions
- ADR-0001 (Postgres is the concurrency authority) — this bug class makes the lock a no-op at the
  application layer, so it strikes directly at ADR-0001's guarantee.
- ADR-0002 (lazy expiry is authoritative) — the reassignment in the exploit is lazy-expiry
  reconciliation, so the race is a direct consequence of that design, not an exotic edge case.
- ADR-0007 (manual hold release reuses EXPIRED status) — `releaseHold` is the method in question.
- CLAUDE.md: `@Transactional` with explicit propagation/isolation for booking logic; keep methods
  small and testable; Flyway for any schema change (none expected here).
