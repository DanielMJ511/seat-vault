# T-003 — Health aggregate matches ADR-0001: Postgres fatal, Redis reported but non-fatal
Milestone: M8 (#19)   Status: pending
Depends on: T-002 (needs a reachable, exposed health endpoint to assert against)

## Description
This is the part of #18 that is a **correctness statement rather than a preference**, and the
reason the issue needed thought rather than just a dependency.

Actuator auto-configures a `RedisHealthIndicator` whenever Spring Data Redis is on the classpath,
and by default every indicator contributes to the aggregate status. So with a naive setup, **Redis
going down would make `/actuator/health` report `DOWN`**, return 503, and cause an orchestrator to
pull a perfectly functional instance out of rotation.

That directly contradicts **ADR-0001**. Redis is explicitly *not* the concurrency authority — it is
a fail-fast optimization layer, and `HoldRedisUnavailableRaceIntegrationTest` exists precisely to
prove the system stays correct with Redis unreachable. `HoldService.createHold` calls
`redisLockService.tryLock` and, with Redis down, `tryLock` fail-opens for everyone and Postgres row
locks alone serialize seat acquisition. A health check that treats Redis as fatal would assert the
opposite of what the architecture claims and what that test already demonstrates.

So: the Redis indicator should be **reported but excluded from the aggregate** (or downgraded),
while Postgres — which *is* authoritative — stays **fatal to readiness**. Whatever shape is
chosen, **the ADR-0001 relationship must be visible in configuration rather than implied** — a
comment in `application.properties` (or wherever the group membership is declared) naming ADR-0001
and saying why.

## SETTLED BY GRILLING (2026-08-16) — see ADR-0013, do not re-decide
**Redis is excluded from readiness by group composition. Nothing suppresses, downgrades, or
misreports it anywhere else.**

```properties
management.endpoint.health.group.readiness.include=readinessState,db
management.endpoint.health.group.liveness.include=livenessState
```

Redis is deliberately absent from the readiness list, with a comment citing ADR-0001. The
top-level `/actuator/health` aggregate keeps the Redis indicator and **reports DOWN honestly** when
Redis is unreachable; it is exposed but authenticated (ADR-0012), so that honesty reaches operators
rather than the internet.

Two alternatives were considered and rejected, both worth knowing so they are not re-proposed:

- **A custom `StatusAggregator` cannot do this.** Verified with `javap` against
  `spring-boot-health` 4.1.0: `getAggregateStatus(Set<Status>)` receives statuses with **no
  component names**, so it has no way to ignore Redis while keeping Postgres fatal. It is the first
  thing anyone reaches for and it does not exist.
- **A custom `HealthIndicator` bean named `redis` that always reports UP** was rejected because,
  combined with `show-components=always` (ADR-0012), an anonymous caller would see
  `"redis":{"status":"UP"}` while Redis was down. A health endpoint is the one surface that must
  not make false statements.

**Departure from issue #19's wording, recorded deliberately:** #19 says *"health reports UP with
Redis stopped."* Under this decision the **parent** reports DOWN and **readiness** reports UP. The
intent — do not evict a working instance — is met. Note it when closing the issue.

## Facts verified during grilling — confirm, don't re-research
- `management.health.redis.enabled` and `management.health.db.enabled` both default to `true`, so
  both indicators are auto-configured and both contribute to the parent aggregate.
- **Boot's default `readiness` group is `readinessState` alone — `db` is NOT a member unless
  named.** So "Postgres is fatal to readiness" is not inherited; it is the line above that creates
  it. This is what makes the ADR-0001 relationship visible in configuration, exactly as #18 asked.
- `management.endpoint.health.validate-group-membership` defaults to `true`, so a typo'd member
  fails at **startup**. A free guard that the rejected custom-indicator approach had no equivalent
  for — worth naming in a comment so it is not disabled casually.

## Acceptance criteria
- Integration tests proving the aggregate semantics, not just the configuration:
  - **With Redis unreachable, the health endpoint still reports UP overall, and hold creation still
    succeeds.** This is the runtime counterpart to `HoldRedisUnavailableRaceIntegrationTest`.
    `BrokenRedisTestConfig` (`src/test/java/com/seatvault/seat_vault/config/`) already exists for
    exactly this — a `@TestConfiguration` `RedisConnectionFactory` pointed at a dead port, which
    produces real `DataAccessException`s through the real Spring Data Redis stack while contained
    to one Spring context. Reuse it. **Do not stop the shared Testcontainers Redis** — M7's grilling
    rejected that explicitly because it breaks every later test in the cached context.
  - **The Redis indicator reports its true (down) state** on the parent aggregate in that same
    scenario, rather than being silently omitted or forced to UP.
  - **Postgres fatal to readiness — asserted behaviourally, NOT by breaking the datasource.**
    Settled by grilling: the context cannot boot without a database (Flyway migrates at startup and
    `ddl-auto=validate` runs after it), so a broken-datasource context is not available and a
    proxy that lies to Hibernate is not worth building for one assertion. Instead, hit
    `/actuator/health/readiness` as an authenticated caller with details on, and assert its
    `components` **contains `db`** and **does not contain `redis`**. That asserts what the live
    aggregate is actually built from and fails the moment anyone edits the include list.
  - **The Javadoc must say which half this proves.** It proves `db` is a readiness member; it does
    not prove that a failing `db` produces DOWN — that is Boot's own aggregation, not ours.
    Per M7's lesson, state what a guard does not cover rather than letting it read as broader
    coverage than it is.
- The ADR-0001 relationship is stated in configuration as a comment, not left implied.
- No regression in `HoldRedisUnavailableRaceIntegrationTest` or `RedisLockServiceTest`.
- Full `./mvnw test` green.

## Relevant conventions
- **ADR-0001** — Postgres is the concurrency authority; Redis is a non-authoritative fail-fast
  optimization layer. This is what makes the Redis-must-not-be-fatal requirement a correctness
  statement.
- **ADR-0002** — lazy expiry is authoritative; also a Postgres-side guarantee, unaffected by Redis.
- CONTEXT.md's language section for the terms used in whatever is written down.
