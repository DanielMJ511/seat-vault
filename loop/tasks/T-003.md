# T-003 — Redis-unavailable fallback proving DB-only locking still holds
Milestone: M7 (#12)   Status: pending

## Description
Make ADR-0001's central claim falsifiable: with Redis unavailable, correctness is unchanged,
because Postgres — not Redis — is the concurrency authority.

`RedisLockService` already implements the fail-open contract (catch `DataAccessException` in
`tryLock`, return `REDIS_UNAVAILABLE_SENTINEL`; `unlock` no-ops on that sentinel). **Neither
branch has any test today** — the whole fail-open path is untested code, and it is precisely
the code that runs during a real outage.

The sharpest framing, and the reason this test is worth writing: `SEAT_ALREADY_HELD` is thrown
from two distinct places — `HoldService:84` on Redis-lock contention, and `HoldService:129` on
a Postgres-level `HELD` seat. **With Redis down, the first path is unreachable.** So the race
provably runs through a different mechanism while producing an identical outcome. That is what
"Redis was never load-bearing for correctness" looks like as an assertion.

**Two mechanisms for two jobs** (decided during grilling):

1. **A throwing stub `StringRedisTemplate`** for isolated `RedisLockService` unit assertions —
   `tryLock` returns the sentinel when the template throws `DataAccessException`, and `unlock`
   given the sentinel makes **no Redis call at all**. A stub is right here because the point is
   observing the *absence* of an interaction.
2. **A `@TestConfiguration` supplying a `RedisConnectionFactory` pointed at a dead port** for
   the end-to-end race. This produces genuine `DataAccessException`s through the real Spring
   Data Redis stack — what `tryLock`'s catch clause actually has to handle — while staying
   contained to one test class.

Stopping the shared Testcontainers Redis was considered and **rejected**: the container is
shared across the cached Spring context, so it would break every subsequent test in that
context. Note in the class Javadoc that mechanism 2 forces a separate Spring context and
therefore costs an extra container startup.

**Scope: hold-stage races only — not the full pipeline.** The claim under test is narrow, and a
hold-stage assertion proves it. Re-running the whole pipeline would mostly re-test T-001 in a
second context against the runtime budget. Two races are needed:

**Race 1 — single-seat, N threads.** Exactly one winner, same as the Redis-up test. This is the
headline fallback proof.

**Race 2 — overlapping multi-seat, and this is the only place it can live.** 8 seats, 12
threads, thread `i` requesting `{i, i+1, i+2} mod 8`. This is the **only configuration in the
whole suite that exercises `HoldService`'s ascending-id Postgres lock ordering** (the
deadlock-avoidance reasoning at `HoldService.java:75`). The reason is specific: while Redis is
up, `createHold` acquires all of a request's Redis locks before any Postgres work, so a thread
with an overlapping seat set is rejected at the Redis tier and never reaches
`findByIdForUpdate` — the ordering loop only ever runs uncontended. With Redis **down**,
`tryLock` fail-opens for every caller, so all 12 threads enter the Postgres loop
simultaneously with overlapping row sets. That is exactly the scenario the ascending-id
ordering exists to prevent from deadlocking, and it has no other test.

Assert: no deadlock, no thread times out, no 500, no seat double-booked, no seat stranded
`HELD`. A Postgres deadlock would surface as a `CannotAcquireLockException` → 500, so the
no-500 assertion is what actually catches an ordering regression here. (T-001 originally
claimed this coverage; that claim was wrong for the reason above and has been corrected.)

## Acceptance criteria
- Full `./mvnw test` green, and **no other test class is destabilized** — run the whole suite,
  not just the new class, and confirm the Redis-down mechanism leaks into no other context.
- With Redis unavailable, `POST /api/holds` on an uncontended seat still returns 201 — the
  service fails open rather than 500-ing.
- Race 1: with Redis unavailable and N threads racing one seat, **exactly one** hold is created
  and the rest are rejected — the same outcome as the Redis-up test, which is the proof.
- Losing threads get `SEAT_ALREADY_HELD` from the Postgres path (`HoldService:129`); the
  fail-fast Redis path is unreachable in this configuration by construction.
- Race 2 (overlapping multi-seat, Redis down): no deadlock, no timeout, no 500, no seat in two
  holds, none stranded `HELD`. Its Javadoc must state that this is the suite's only coverage of
  the ascending-id ordering and why Redis-up cannot reach it — otherwise a future reader may
  "simplify" it back into T-001 and silently lose the coverage.
- `RedisLockService#tryLock` returns the sentinel on `DataAccessException`; `unlock` given the
  sentinel provably makes no call on the template.
- Class Javadoc names ADR-0001 explicitly, so the link from evidence to decision survives.

## Relevant conventions
- **Read ADR-0001 before writing anything here** — this task exists to make it falsifiable.
- `RedisLockService`'s class Javadoc states the fail-fast / fail-open split precisely. Assert
  that contract, not a reinterpretation of it.
- `REDIS_UNAVAILABLE_SENTINEL` is package-private `static final` on `RedisLockService`; a test
  in the same package can reference it rather than duplicating the literal.
- `RedisTestcontainersConfig` / `PostgresTestcontainersConfig` / `TestcontainersConfig` — the
  split exists so a test starts only the containers it needs. This task needs Postgres real and
  Redis broken, so it should import `PostgresTestcontainersConfig` plus its own broken-Redis
  config, **not** `TestcontainersConfig`.
- CLAUDE.md: no mocks for infrastructure in integration tests. A stub for the isolated
  `RedisLockService` unit assertions is fine and is not the integration test.
