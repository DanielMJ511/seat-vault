# T-007 — Fix the holds↔seats lock-order inversion between releaseHold and createHold
Milestone: M7 (#12)   Status: pending
Escalation: spawn `implementer` directly — this is a live production deadlock requiring a
lock-ordering decision, not a mechanical change.

## Description
`HoldService` acquires the `holds` and `event_seats` row locks in **opposite orders** in its two
concurrency-critical methods. That is a textbook ABBA deadlock, and Postgres resolves it by
killing one transaction — which surfaces as a 500 on a legitimate request.

**Correction (found during implementation): there were three offenders, not two.**
`BookingService.createFromHold` also locked holds→seats — it locks the hold to authorize, then the
seats — so it deadlocked against `createHold` and the sweep for exactly the same reason
`releaseHold` did, on an entirely mundane trigger: a user clicking "book" on a hold that lazily
expired moments earlier while someone else takes the seat. A fix covering only `releaseHold`
would have left that live. The table below is corrected.

| Method | Locks first | Locks second |
| --- | --- | --- |
| `releaseHold` | the `holds` row (`findByIdForUpdate`, ~line 165) | each `event_seats` row (~line 196) |
| `BookingService.createFromHold` | the `holds` row (to authorize) | each `event_seats` row |
| `createHold` → `createHoldWithSeatsLocked` | each `event_seats` row (~line 116) | the `holds` row — implicitly, when the stale-hold reconciliation at ~line 141 dirties it and Hibernate flushes an UPDATE |
| `HoldSweepService.sweepExpiredHolds` | `event_seats` rows, via `releaseExpiredHeldSeats()` | the `holds` row, via `expireOverdueHolds()` in the **same** transaction |

**There are two offenders on the seats→holds side, not one.** The sweep was found during T-006's
code review: its two bulk statements run in one transaction and match the same expired hold by
construction (same `now`, same predicate), so it deadlocks against `releaseHold` for exactly the
same reason `createHold` does. Any fix must cover both, and a fix that only reorders `createHold`
leaves the sweep broken. Note the sweep runs on a 30-second `@Scheduled(fixedDelay)`, so this
path fires unattended in production rather than needing a user to trigger it.

The interleaving: thread A (`releaseHold(H)`) holds H's row and waits on seat 1. Thread B
(`createHold` on seat 1) holds seat 1 and waits to update H during lazy-expiry reconciliation.
Neither can proceed. Postgres detects the cycle and aborts one with `CannotAcquireLockException`,
which `GlobalExceptionHandler`'s catch-all turns into a 500 `INTERNAL_SERVER_ERROR`.

**This is empirically confirmed, not theoretical.** During T-006, `implementer` ran two probes
against real Postgres: one observed the competing `createHold` blocked with `ungrantedLocks=1`
and unfinished after 3s; the other observed Postgres raise `deadlock detected` outright. Both
probes were throwaway and are not in the repo — reproducing them is part of this task.

Note the second lock in `createHold` is **invisible at the call site**: nothing there reads like
a lock acquisition. It is Hibernate flushing a dirty entity. That is why the existing
deadlock-avoidance comment at `HoldService.java:75` — which is about ordering *seats among
themselves* by ascending id — does not cover this case at all, and why the inversion survived
review until now.

## Why this is separate from T-006 — and how the coupling resolved
T-006 fixed the stale-entity read in `releaseHold`. That fix is correct and stands. T-006 also
established that the clobber it prevents was **latent**, precisely *because* the hold row lock
serialized the two methods. The masking of one bug was caused by the mechanism creating this one.

**Outcome (confirmed during implementation): T-006's fix is now load-bearing, not
defense-in-depth.** With the hold lock moved last, a competitor *can* commit a re-homing while a
release is parked on an earlier seat — so the interleaving T-006 guards against became reachable
the moment this task landed. Verified by deleting the ownership guard post-fix and watching
T-006's regression test fail (`expected: HELD but was: AVAILABLE`), then restoring it.

ADR-0010's caveat said the masking was "one lock in one method away from being false." It was
false one task later. Reverting ADR-0010's discipline now costs a live double-booking rather than
a theoretical one, and ADR-0010 was updated to say so.

## Description of the fix
Two candidate directions; choose deliberately and record the reasoning.

**A. Make `releaseHold` take the seat locks before the hold lock** — i.e. invert it to match
`createHold`'s seats→hold order. Complication: `releaseHold` currently needs the hold row *first*
to authorize the caller (ownership check) and to read the candidate seat list. Reordering means
gathering candidate seat ids unlocked, locking the seats in ascending id order, then locking and
re-validating the hold — and re-checking that each seat still belongs to the hold under its lock
(which T-006's ownership guard already does). Watch that the ownership/404 semantics of ADR-0008
and the `HOLD_NOT_ACTIVE` behaviour are preserved.

**B. Stop `createHold` writing the stale hold inside the seat loop** — defer the lazy-expiry
reconciliation (`staleHold.setStatus(EXPIRED)`) so `createHold` never takes a hold lock while
holding seat locks. ADR-0002 makes the lazy check authoritative and the stored status merely
reconciliatory, and `HoldSweepService` already exists to reconcile in bulk — so *not* writing it
inline may be legitimate. Verify that against ADR-0002 before relying on it; if the reconciliation
is load-bearing for anything else, this option is out.

Option B looks smaller and less risky, but A is the more conventional fix (consistent global lock
ordering). Weigh them; do not just take the cheaper one without saying why.

Also consider whether a `@Transactional(timeout = ...)` or a statement-level lock timeout should
back-stop the ordering discipline, so a future inversion degrades into a timeout rather than an
indefinite block. That is a suggestion, not a requirement.

## Acceptance criteria
- **A regression test that reproduces the deadlock against the current code and passes after the
  fix.** Assert on the absence of a 500 / `CannotAcquireLockException` for a legitimate
  release-racing-create, not merely that "something completed." Model the deterministic
  two-thread coordination on `HoldReleaseSeatLockRaceIntegrationTest` (T-006), which parks one
  thread and polls `pg_locks` rather than sleeping. Confirm it fails pre-fix and report that
  output — a test that passes before the fix proves nothing.
- After the fix, every path that touches both tables acquires them in one consistent order, and
  that order is stated in a comment at both sites.
- **T-006's regression test still passes**, and the latent clobber it guards against is still
  guarded — verify explicitly that the fix does not unmask it.
- No regression in `HoldServiceTest`, `HoldIntegrationTest`, `NoOversellIntegrationTest`,
  `HoldRedisUnavailableRaceIntegrationTest`, or `BookingIntegrationTest`'s
  `concurrentReleaseAndCreateFromHoldOnSameHoldResolvesConsistently`.
- Full `./mvnw test` green.

## ADR
Extend **ADR-0010** rather than writing a new ADR, if the resulting rule is naturally the same
discipline ("the order in which these two tables are locked is part of the contract"). If the
lock-ordering rule stands on its own, write **ADR-0011** instead and cross-reference 0010. Use
your judgement; do not write both.

Whichever you choose must make the invisible-lock hazard explicit: dirtying a managed entity
takes a row lock at flush time, so lock order is not always readable from the call site.

## Carried forward from T-006's code review (unaddressed there)
T-006 was APPROVED with three non-blocking items. A follow-up attempt to fix them was cut short
by an API session limit before making any changes, so they land here — this task touches the same
test file and the same lock machinery, so it is the natural place.

1. **(Most significant — fix this one properly.)** `awaitBlockedOnARowLock()` in
   `HoldReleaseSeatLockRaceIntegrationTest` (~lines 241-259) polls
   `select count(*) from pg_locks where not granted`, unscoped by relation and by PID.
   `HoldSweepService` runs on a 30-second `@Scheduled(fixedDelay)` with `@EnableScheduling`
   ungated by profile, and Spring's context cache keeps that scheduler live across a full suite
   run. The test's `@BeforeEach` deliberately pushes the hold's `expiresAt` into the past —
   exactly the state the sweep hunts for — so a sweep firing mid-poll could produce an ungranted
   lock that satisfies the poll, unblock the thief early, and pass the test for the wrong reason.
   Not observed in practice (isolated runs ~15-17s with the poll resolving in ~1.5s; full-suite
   runs green), so it is latent rather than active — but it contradicts the helper's own claim of
   "no sleep-and-hope window."

   Scope the query to the `event_seats` relation and ideally the specific blocked PID (join
   `pg_locks` to `pg_class` and/or `pg_stat_activity`). Observe the actual lock shapes first
   rather than guessing the predicate. Prefer this over disabling scheduling for the test profile
   — it keeps the fix local instead of changing app-wide config other tests may lean on. Note
   this interacts with T-007's own work: once the sweep's lock-order inversion is fixed, the
   sweep's interference profile changes, so re-verify the poll afterwards.

2. The same test's "What the thief models" javadoc (~lines 76-92) should state plainly that the
   thief transaction is **manufactured** and bypasses `HoldSweepService`, rather than reading like
   a natural production sequence. It is legitimate as a forward-looking guard for ADR-0010's
   discipline — just say so, to the standard ADR-0010 already sets by calling the masking "an
   accident of the current call graph, not a guarantee."

3. Trivia: a javadoc line reference cites `HoldService.java:163` for the hold-row lock where the
   actual `findByIdForUpdate` is at 165 (163 is a comment). ADR-0010's paragraphs are denser than
   the house style of ADR-0001/0002 — consider breaking up the longest ones, but do not rewrite
   it wholesale; its content is correct and correctly hedged.

## Relevant conventions
- ADR-0001 (Postgres is the concurrency authority) — a deadlock-induced 500 on a valid request is
  a direct failure of that guarantee's usability.
- ADR-0002 (lazy expiry is authoritative) — central to whether option B is legitimate.
- ADR-0007 (manual hold release reuses EXPIRED status), ADR-0008 (404 not 403 on ownership
  mismatch) — must survive any reordering of `releaseHold`'s authorization step.
- ADR-0010 (no unlocked entity reads before a row lock) — T-006's rule; must not be undermined.
