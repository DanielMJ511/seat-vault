# T-004 — `HEALTHCHECK` on the app image and its compose service
Milestone: M8 (#19)   Status: pending
Depends on: T-002 (the URL), T-003 (that URL being the *right* one)

## Description
`docker-compose.yml` declares healthchecks on `postgres` (`pg_isready`) and `redis` (`redis-cli
ping`), and the `app` service declares none — so `app` is the only component whose readiness is
unobservable, and `depends_on: condition: service_healthy` cannot be pointed at it. Add a
`HEALTHCHECK` to the `Dockerfile` and a matching `healthcheck:` to the compose `app` service, so
the app matches the two services beside it.

## SETTLED BY GRILLING (2026-08-16) — do not re-decide
- **Endpoint: `/actuator/health/readiness`.** Forced by ADR-0012/0013 rather than merely preferred:
  the parent `/actuator/health` is authenticated, so a healthcheck could not use it even if you
  wanted to. It is also the semantically correct target — `depends_on: condition: service_healthy`
  asks whether traffic may be routed here, not whether the process should be restarted. Polling the
  parent would additionally let Redis mark the app unhealthy, undoing ADR-0013 through the back door.
- **Declared in the `Dockerfile` only.** `docker-compose.yml` gets a short comment pointing at the
  image's `HEALTHCHECK` rather than duplicating it. `depends_on: condition: service_healthy` reads
  the container's health status, which comes from the image, so a compose block would restate what
  already works and could drift out of sync. **This is a deliberate departure from #19's wording,
  which asks for both** — note it when closing the issue.
- **Timings: `--start-period=40s --interval=10s --timeout=3s --retries=3`, with `start-period`
  tuned from observed startup.** The neighbours' `interval: 5s, timeout: 5s, retries: 5` suits
  Postgres and Redis; a Boot app running Flyway migrations at startup takes far longer, and without
  a start period the container is marked unhealthy during a normal boot and thrashes. Failures
  during the start period do not count against retries, which is exactly the behaviour wanted here.
- **Tool: `wget --spider -q`, pending verification.** The runtime stage is
  `eclipse-temurin:25-jre-alpine`, which is BusyBox-based, so `wget` should be present and `curl`
  almost certainly is not. **This could not be verified during planning — Docker was not running on
  the planning machine.** Confirm inside the actual image before relying on it. If `wget` is absent,
  the options are installing a tiny client (adds a layer and attack surface) or a JVM-based check
  (spawns a whole JVM every interval — expensive at a 10s cadence). Report what you found.

## Acceptance criteria
- `HEALTHCHECK` instruction in `Dockerfile`, with a comment explaining the endpoint choice and the
  tool choice (the file's existing comments set the standard for explaining non-obvious decisions —
  see the tests-skipped and JWT_SECRET blocks). It should say why readiness rather than the parent
  aggregate, citing ADR-0013.
- A comment in `docker-compose.yml`'s `app` service pointing at the image's `HEALTHCHECK` and
  saying the omission is deliberate, so nobody adds a duplicate later.
- No management port exists (ADR-0012 keeps actuator on 8080), so the existing `ports: 8080:8080`
  mapping is unchanged — confirm rather than assume.
- **Verification is manual and belongs to the user**: `docker compose --profile app up -d --build`
  shows the `app` service reaching `healthy`, not just `running`. There is no automated test for a
  Docker `HEALTHCHECK` in this suite, and building the image requires a Docker daemon. Record this
  explicitly as a user-action verification step in `loop/STATE.md` rather than claiming it passed.
  If the environment does have a working Docker daemon and building is feasible, do run it and
  report the actual `docker compose ps` output — but do not fabricate it.
- Full `./mvnw test` green (this task should not affect the suite at all; confirm it did not).

## ADR
**None.** ADR-0013's final paragraph already records why the healthcheck polls readiness. This task
applies decisions made in T-002/T-003 to the container surface; it makes none of its own.
