# T-001 — Gate `@EnableScheduling` under the `test` profile
Milestone: M9 (#22)   Status: pending
Closes: #21

## Description

`@EnableScheduling` sits on `SeatVaultApplication` with no profile gate, so the real 30-second
`HoldSweepService` tick is live in every Spring context a test starts — and keeps ticking for the
whole JVM lifetime, because Spring caches contexts across test classes.

M8/T-005 established the scope empirically (identity hashes of the injected `ApplicationContext`,
`MeterRegistry`, and the live JDBC URL, printed during a full suite run). **Ten classes share one
context**, because they carry a byte-for-byte identical annotation set
(`@SpringBootTest @AutoConfigureMockMvc @Import(TestcontainersConfig.class) @ActiveProfiles("test")
@TestPropertySource(...seed)`): `AuthIntegrationTest`, `BookingConfirmLoadIntegrationTest`,
`BookingIntegrationTest`, `EventIntegrationTest`, `EventSeatIntegrationTest`, `HoldIntegrationTest`,
`NoOversellIntegrationTest`, `SecurityConfigIntegrationTest`, `VenueIntegrationTest`,
`GlobalExceptionHandlerIntegrationTest`. One context, one `MeterRegistry`, one database, one live
sweep.

Several of them are deliberately not `@Transactional` — they commit real multi-seat holds so row
locks mean something — and those committed holds carry the default 5-minute TTL. The suite finishes
in roughly 80 seconds, so today nothing ages into sweep range mid-run.

**That is a coincidence, not a guarantee.** A slower CI runner, a growing suite, or one added
`Thread.sleep` flips it, and the failure presents as an unrelated test flaking intermittently — the
hardest kind to diagnose, and the kind most likely to be "fixed" by weakening a real assertion. It
already came close once: T-005's first implementation asserted an absolute value on a
`DistributionSummary#max()`, which a background tick reclaiming a sibling's multi-seat hold would
have broken. Caught in review, reworked to diff cumulative statistics, and the flakiness was
*reproduced deliberately* by injecting a sibling recording a 3-seat batch. The assertion is safe
now; the underlying hazard is untouched.

## SETTLED — do not re-decide

**Gate the scheduling, never the bean.**

`HoldSweepService` must remain a live, injectable bean. Three tests inject it and call
`sweepExpiredHolds()` directly:
- `HoldIntegrationTest#sweepReclaimsAnExpiredHeldSeatAndExpiresItsHold` (~line 435)
- `HoldIntegrationTest#idleSweepRecordsZeroRatherThanSkippingTheMetric` (~line 490)
- `HoldSweepSeatLockOrderIntegrationTest` (~line 191)

Removing or conditionalizing the `@Component` breaks all three. Suppressing
`ScheduledAnnotationBeanPostProcessor` registration breaks none — **which is exactly why this fix
costs zero coverage.** Gating removes uncontrolled writes, not tested behaviour.

**Explicitly rejected: shortening `hold.ttl-minutes` in `application-test.properties`.** This looks
like it would help and does the opposite — a shorter TTL makes committed holds age out *faster*,
increasing the odds a background tick reclaims a multi-seat batch mid-suite. It tightens the
coincidence rather than removing it. (The second M8 review was explicit that the two candidate
fixes are not equivalent, correcting the orchestrator's own framing.)

## Approach — SETTLED by grilling (2026-08-17)

Move `@EnableScheduling` off `SeatVaultApplication` onto a small dedicated `@Configuration` class
gated with:

```java
@ConditionalOnProperty(name = "seatvault.sweep.scheduling.enabled", matchIfMissing = true)
```

- Write the default **explicitly** as `seatvault.sweep.scheduling.enabled=true` in
  `application.properties`, so there is no invisible default to reason about.
- `matchIfMissing = true` is the backstop for someone deleting that line, not the primary mechanism.
- Set `seatvault.sweep.scheduling.enabled=false` in `application-test.properties`.

**Rejected: `@Profile("!test")`**, which is what #21 literally proposed. It ties production
reconciliation to a profile *name*, and "test" is exactly the kind of name a deployed staging
environment gets — someone running with `SPRING_PROFILES_ACTIVE=test` would silently kill the sweep
with no signal, which #21 itself calls a far worse outcome than the flakiness being fixed. With a
property defaulting on, disabling reconciliation always requires an explicit, greppable act. It also
puts the gate in `application-test.properties`, where a test author actually looks.

The Javadoc on the new class is load-bearing: it must say *why* the gate exists (the shared-context
hazard above) and *why it must not be widened*, because the next author's instinct on seeing a
disabled scheduler will be to remove the gate or broaden it.

## Acceptance criteria

**The gate must be proved by observation, in both directions.** Per the standing repo rule, a guard
only counts if it can observe the failure it claims to catch — reading the annotation does not count.

1. **Under `test`, no scheduled task is registered.** Inspect the context's actual scheduled tasks
   (`ScheduledTaskHolder#getScheduledTasks()` / `ScheduledAnnotationBeanPostProcessor`) and assert
   none targets `HoldSweepService#sweepExpiredHolds`. Grilling confirmed `sweepExpiredHolds` is
   currently the **only** `@Scheduled` method in main, so "no tasks at all" happens to be equivalent
   today — but assert on the sweep specifically, so the test keeps its meaning when something else
   gets scheduled.
2. **With the property absent, the sweep task *is* registered.** Not optional. **Gating too broadly
   would silently disable production reconciliation, a far worse outcome than the flakiness this
   fixes** — and a one-directional test cannot tell the two apart.

   Use a real `@SpringBootTest @ActiveProfiles("dev") @Import(PostgresTestcontainersConfig.class)`
   context. **Why `dev` and not "no profile":** grilling established that
   `JwtProperties.validate()` (`JwtProperties.java:59`) throws unless `dev` or `test` is active, so a
   profile-less context cannot boot in tests at all. `application-dev.properties` does not set the
   sweep property, so this context falls through to `application.properties` — meaning the test
   exercises the **actual production value**, not a fixture.

   **Rejected: `ApplicationContextRunner`.** It would assert the condition evaluated, not that a task
   registered — which is condition-reading wearing a test's clothes.
3. `HoldSweepService` is still injectable, and the three direct-call tests above still pass.
4. Full `./mvnw test` green.

## The `dev` test runs a live scheduler — this is accepted, and must be documented

Criterion 2 boots a context whose scheduler really does tick every 30 seconds, cached for the JVM
lifetime. That is the exact condition this task removes, so the reasoning has to be written down.

**Why it is safe here:** that context is isolated. Its profile and imports give it a distinct
`MergedContextConfiguration` cache key, so it gets its own Spring context *and* its own Postgres
container (containers are plain `@Bean`s with no Testcontainers reuse). No other class shares it, the
class commits no fixtures, and it asserts only task registration. The M8 hazard was specifically
about *shared* state — a tick reclaiming a sibling's committed multi-seat holds — and here there are
no siblings to act on.

**Put this in the class Javadoc, as a load-bearing comment.** It is not self-evident: a future
reader finding a test that deliberately runs the scheduler M9 just disabled will either panic or,
worse, copy the pattern into a class that *does* share a context. State what would break the
argument — adding `@AutoConfigureMockMvc`, or any annotation change that merges its cache key with
another class.

**Rejected:** shutting the scheduler down after the class, which adds machinery to solve a problem
isolation already solves.

## Also in scope — the correction #21 missed

#21 names two tests to revisit. **There are three.** Update every Javadoc that documents the old
behaviour, in this same change:

- `HoldReleaseSeatLockRaceIntegrationTest` (~line 276) — **the one #21 missed.** Its
  `awaitReleaseBlockedOnTheSeatRow` Javadoc explains PID-scoping by citing "`HoldSweepService` runs
  every 30 seconds, `@EnableScheduling` is not gated by profile, Spring's context cache keeps that
  scheduler alive for the whole suite."
- `HoldLockOrderDeadlockIntegrationTest` — same class of comment.
- `HoldSweepSeatLockOrderIntegrationTest` — same.
- `HoldIntegrationTest` (~lines 60–115) — its shared-context Javadoc **keeps** its `MeterRegistry`
  half (still accurate, and still the reason the assertions diff cumulative statistics) and **loses**
  its background-tick half.

**Keep the PID-scoped polling itself.** It is good practice regardless of the scheduler, and
removing it would trade one latent flake for another. Only the *why* changes.

M8's retro lesson applies directly: *a fact worth stating twice will drift; when you correct one
instance, grep for every other and fix them in the same change.* Before calling this done, grep the
repo for `EnableScheduling`, `30 seconds`, `30_000` and `background tick` and confirm no stale
claim survives — **except** historical `loop/STATE.md` entries, which are never rewritten.
