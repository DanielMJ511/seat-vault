# T-001 — No-oversell suite: hold-stage contention over a seat pool
Milestone: M7 (#12)   Status: pending

## Description
Add an integration test class racing many threads through the full
`POST /api/holds` → `POST /api/bookings` → `POST /api/bookings/{id}/confirm` pipeline over a
small private pool of EventSeats, asserting no oversell. Two race shapes, two invariants.

**Shape (a) — round-robin, exact count.** 5 seats, 20 threads; thread `i` targets seat
`i % 5`. Every seat is guaranteed at least one attempt, so exactly 5 threads win and 15 lose.
`booked_count == seat_count` holds *exactly and deterministically* — assert equality, not a
bound.

**Shape (b) — overlapping multi-seat holds.** 8 seats, 12 threads, each requesting 3
consecutive seats (thread `i` wants `{i, i+1, i+2} mod 8`). With 8 seats and 3-seat requests,
two disjoint requests can both succeed, so **multiple concurrent multi-seat holds can commit
simultaneously** — an invariant shape (a) cannot produce, since it is single-seat-per-thread.
That is what this shape is for.

Note the invariant genuinely weakens here and that is correct, not a bug in the test: hold
creation is all-or-nothing, so a thread that wins seat 3 and loses seat 4 rolls back both, and
a seat can end `AVAILABLE` because everyone who wanted it also wanted something they couldn't
get. Assert "no seat appears in two bookings, no deadlock, no 500" — **do not** assert
`booked_count == seat_count` for this shape.

**This shape does NOT exercise `HoldService`'s ascending-id Postgres lock ordering
(`HoldService.java:75`), and the Javadoc must not claim it does.** `createHold` acquires
*all* of a request's Redis locks (non-blocking `SETNX`) before any Postgres work and holds
them through the `finally` — so while Redis is up, two threads with overlapping seat sets can
never both be inside `createHoldWithSeatsLocked`. The loser is rejected at the Redis tier
before it ever calls `findByIdForUpdate`, meaning the Postgres ordering loop only ever runs
for a thread whose seats nobody else can be holding. State this as a known gap in the
Javadoc. The ordering path is reachable only with Redis *down* (where `tryLock` fail-opens for
everyone and all threads flood Postgres at once) — that coverage now lives in **T-003**.

**Known and accepted limitation, to be stated in the class Javadoc:** contention here bites
only at the hold stage. Holds are single-owner by construction, so a thread that wins its hold
books and confirms unopposed. Load on the booking and confirm stages is T-002's job — say so
in the Javadoc so a future reader doesn't mistake this for full-pipeline contention.

Build a private Venue/Event/Seats in `@BeforeEach` following `BookingIntegrationTest#setUp`
exactly, **including the far-future `startsAt`** (`Instant.now().plus(400, ChronoUnit.DAYS)`)
and the reason: this class cannot be `@Transactional` (each thread needs its own real
transaction and connection for the row locks to mean anything), so every row really commits
and must not perturb `EventIntegrationTest`'s startsAt-ordering assertions.

## Acceptance criteria
- Full `./mvnw test` green, and green across repeated runs — a race test that passes only
  sometimes is worse than none. Whole-suite budget is ~3 minutes.
- Shape (a): exactly 5 seats end `BOOKED`, exactly 5 bookings reach `CONFIRMED`, 15 threads are
  rejected, and no `EventSeat` appears in more than one `BookingSeat` across all bookings.
- Shape (b): no `EventSeat` in two bookings; no thread deadlocks or times out; every seat ends
  either `BOOKED` (by exactly one booking) or `AVAILABLE` — none stranded `HELD` with a dead
  `current_hold`. Derive winners from actual results rather than hard-coding a count, so the
  assertions stay correct regardless of how many disjoint requests happen to win.
- Shape (b)'s Javadoc states plainly that the Postgres ascending-id ordering path is *not*
  covered here and points to T-003 — do not claim coverage the test doesn't deliver.
- No thread receives a 500 in either shape. An `INTERNAL_SERVER_ERROR` under contention is a
  defect this suite exists to catch — assert its absence explicitly.
- Losing threads fail with `SEAT_ALREADY_HELD` or `SEAT_ALREADY_BOOKED` (per ADR-0009 these are
  the only contention codes reachable at the hold stage, and neither changes in T-004).
- Assertions run from a fresh transactional read after all threads join, never from entities
  captured mid-race (see `HoldIntegrationTest:260-266` for why lazy proxies bite here).
- Incidentally assert ADR-0003: each CONFIRMED booking's payment amount equals the sum of its
  seats' hold-time price snapshots.

## Relevant conventions
- **Add `spring.datasource.hikari.maximum-pool-size=30` to
  `src/test/resources/application-test.properties`** before writing either shape. HikariCP
  defaults to 10 and `findByIdForUpdate` has no lock timeout, so a thread blocked on a row lock
  holds its connection; past ~10 threads you measure connection starvation, and Hikari's 30s
  acquisition timeout surfaces as a 500 that this suite would report as a false defect.
- ADR-0001 (Postgres is the concurrency authority) — the row lock is the mechanism under test.
- ADR-0002 (lazy expiry is authoritative) — `hold.ttl-minutes` is 5, so holds will not expire
  mid-race naturally; don't build the test around expiry.
- ADR-0003 (price locked at hold creation).
- CLAUDE.md: real Postgres/Redis via Testcontainers `@ServiceConnection`; no H2, no mocks.
  Docker must be running. Boot 4 per-technology test starters only.
- `HoldIntegrationTest#concurrentHoldRequestsForSameSeatOnlyOneWins` is the closest existing
  pattern (latch, executor, futures with timeout, `finally` shutdown) — follow its structure.
