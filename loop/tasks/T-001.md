# T-001 — BookingService.cancel (service layer, row-locked)

Milestone: M6 (#11)   Status: pending

## Description

Add a `cancel(Long userId, Long bookingId)` method to `BookingService` (`src/main/java/com/seatvault/seat_vault/service/BookingService.java`), mirroring the existing `confirmPayment` method's structure:

1. Lock the `Booking` row via `bookingRepository.findByIdForUpdate(bookingId)`.
2. Reject not-found-or-not-owned the same way `confirmPayment` does (404, matching existing error code convention).
3. Reject if `status != CONFIRMED` with a 409 (new error code, e.g. `BOOKING_NOT_CONFIRMED`, matching the style of existing codes like `HOLD_NOT_ACTIVE`).
4. Reuse the existing `releaseBookingSeats(bookingId)` logic (currently `private`) to lock and free each seat back to `AVAILABLE` with `currentHold = null` — widen its visibility (package-private is enough; it's called from within `BookingService` either way, so only widen if a cleaner call site needs it).
5. Set `Booking.status = CANCELLED` (already exists in the `BookingStatus` enum, unused until now) and set `updatedAt` manually (the entity only has `@PrePersist`, not `@PreUpdate`).

## Acceptance criteria

- Cancelling a CONFIRMED booking the caller owns: seats become `AVAILABLE`, `currentHold = null`, booking status becomes `CANCELLED`.
- Cancelling a booking that doesn't exist or isn't owned by the caller: 404.
- Cancelling a booking that isn't CONFIRMED (PENDING, FAILED, or already CANCELLED): 409.

## Relevant conventions

- Bare `@Transactional` (no explicit isolation level), matching `confirmPayment` exactly — correctness comes from the pessimistic row lock via `findByIdForUpdate`, not the isolation level.
- `ApiException(HttpStatus, code, message)` for all error paths; use ADR-0008's convention (404 for not-found-or-not-owned) for the ownership check.
- ADR-0007 precedent: don't invent a new status — reuse `CANCELLED` (already exists) and `AVAILABLE`/`EXPIRED` conventions already established — no new enum values.
- Do **not** touch `Hold.status` or `Payment.status` — `Hold` is already `CONVERTED` by the time a booking can be CONFIRMED, and `CONTEXT.md` explicitly states cancel leaves `Payment` at `SUCCEEDED` (no refund concept).
- The only concurrency case that applies here is double-cancel (two concurrent cancel calls on the same booking) — resolved automatically by the row lock the same way `confirmPayment`'s idempotency already works; no special-case code needed beyond the standard lock-then-check-status pattern.
