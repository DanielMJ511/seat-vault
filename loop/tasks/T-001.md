# T-001 — Sweep locks `event_seats` in ascending id order (#16) + deadlock regression test
Milestone: M8 (#19)   Status: pending

## Description
`HoldSweepService.sweepExpiredHolds()` calls `EventSeatRepository.releaseExpiredHeldSeats(now)`,
which is a single bulk `UPDATE ... WHERE status = HELD AND currentHold.expiresAt < :now`. Postgres
locks the rows that statement matches **in whatever order the plan produces them** — a sequential
scan, an index scan on `idx_event_seats_current_hold`, or something else as statistics change.

Every other multi-seat path locks seats in **ascending id order** deliberately —
`HoldService.createHold` sorts its seat ids (`.distinct().sorted()`) and the comment above the
locking loop says why. So the sweep can lock seats 7 then 3 while a concurrent multi-seat hold
locks 3 then 7. Postgres detects the cycle, aborts one side with `CannotAcquireLockException`, and
`GlobalExceptionHandler`'s catch-all turns that into a **500 on a legitimate user request**.

This is the residual **seat-versus-seat** case. #12/T-007 (ADR-0011) fixed the **table-versus-table**
ordering — every path now touches `event_seats` before `holds` — and explicitly disclosed this one
rather than addressing it, to keep that change scoped. It is recorded in ADR-0011's Consequences
section.

**Severity: genuine but rare.** It needs the 30-second sweep to fire while a multi-seat hold is in
flight over an overlapping, currently-expired seat set.

## Description of the fix — SETTLED BY GRILLING (2026-08-16)
Do not re-derive this; it was decided and the reasoning is in ADR-0011's new section.

**Issue #16's proposed shape is not a fix, and must not be built.** "Select the target ids ordered,
then `UPDATE ... WHERE id IN (:ids)`" changes nothing: the `SELECT` is unlocked, so it acquires no
row locks and ordering it orders nothing, and the planner remains free to reorder the `UPDATE`'s
`IN` list. That ships two statements, an ordering comment, and the identical bug — worse than the
bug alone, because it reads as fixed.

**The ordering statement must be the one that takes the locks:**

1. A **native** `SELECT id FROM event_seats es WHERE <the existing predicate> ORDER BY es.id
   FOR UPDATE OF es`, returning `List<Long>`. Postgres places the row-locking step above the sort in
   the plan, so rows are locked in ascending id order.
2. Then the existing bulk `UPDATE`, which now only re-touches rows this same transaction already
   holds locks on — so its own plan order stops mattering.

Three details are load-bearing:

- **`FOR UPDATE OF es`, never bare `FOR UPDATE`.** The predicate joins `holds`, and a bare
  `FOR UPDATE` would take the `holds` row locks *in the same statement* — violating ADR-0011's main
  rule while fixing its residual.
- **Native, not JPQL.** Hibernate will not reliably emit `FOR UPDATE` for a scalar JPQL projection.
  It is still a scalar id projection, so ADR-0010 is satisfied — but confirm the generated SQL
  rather than trusting the annotation.
- **Still a scalar projection (ADR-0010).** Do **not** materialize managed `EventSeat` entities to
  gather the ids. An unlocked entity read poisons Hibernate's identity map so a later locked read
  returns pre-lock data — exactly how the double-booking in #12 happened. `EventSeatRepository`
  already has two projections built for this reason, `findIdsByCurrentHoldId` and
  `findDistinctEventIdsByIdIn`; their Javadoc is the house pattern to follow.

Remaining implementation judgement (small, yours to make): the two statements see the world at two
moments, but every id returned by (1) is locked by (1), so no row can change between them. Keep the
full predicate on the `UPDATE` anyway so a stale or empty id list is a no-op rather than a wrong
write, and handle the empty-list case so the `UPDATE` is skipped rather than issued with an empty
`IN ()`.

## Acceptance criteria
- **A regression test that fails against the current (unfixed) code and passes after the fix.**
  Run it pre-fix, watch it fail, and report that output — a test that passes before the fix proves
  nothing.

  **Shape settled by grilling: assert the lock order directly. Do NOT stage a deadlock.**
  A deadlock is a *consequence* of unordered locking; the ordering is the property, and asserting
  it directly is far more deterministic than four-way thread choreography.

  - Park a transaction on the **low-id** seat. Run the sweep on another thread. Then assert via
    `pg_locks` that **while the sweep is blocked on the low-id seat, it holds no lock on the
    high-id seat.** Pre-fix the sweep grabbed the high seat first and this fails; post-fix it went
    for the low seat first and holds nothing. One background thread, no cycle to orchestrate.
  - `HoldLockOrderDeadlockIntegrationTest` (`src/test/java/com/seatvault/seat_vault/service/`) is
    the model for the *mechanics*: it polls `pg_locks` **scoped by backend PID and by relation**
    rather than sleeping, precisely because the live 30-second sweep in the shared Spring context
    can otherwise satisfy a wait on the wrong session's behalf. Reuse `awaitBlockedOnRowLockIn`
    and `locksHeldBy` rather than reinventing them.
  - **Forcing the plan order is still required**, and is the part most likely to produce a test
    that passes for the wrong reason: a freshly inserted pair of seats usually scans in id order
    anyway. The lever: a row that gets `UPDATE`d moves to a later physical position, so inserting
    seat A (low id) then B (high id) and then touching A puts A physically *after* B, and a scan
    yields **B before A**. This should hold whether the planner picks a sequential scan or an index
    scan on `idx_event_seats_current_hold` (V10), since both fall back to physical order for rows
    sharing a hold. **Verify against real Postgres (`EXPLAIN`, plus observing actual lock
    acquisition) before building the test on it.** If it does not hold, find and report a shape
    that does; do not ship a test whose premise you have not observed.
  - **The test must assert its own premise**: check that the unordered scan really does yield
    B before A, and fail loudly with "this test's premise no longer holds" if not. Otherwise a
    future planner change silently turns it into a no-op that reads as coverage.
  - In the Javadoc, cross-reference `HoldLockOrderDeadlockIntegrationTest` as the choreographed
    version of the same family of bug, and state plainly that this test asserts lock *order* rather
    than reproducing the deadlock that unordered locking causes.
- **`HoldIntegrationTest#sweepReclaimsAnExpiredHeldSeatAndExpiresItsHold` still passes.** The
  sweep's *behaviour* must not change, only its lock order. Note that test clears the persistence
  context after the sweep because the bulk update runs as raw SQL against the same connection; if
  the fix changes statement shape, check whether that comment is still accurate and update it if not.
- **ADR-0011 survives.** The sweep still touches `event_seats` before `holds`, and
  `expireOverdueHolds()` still runs after `releaseExpiredHeldSeats()` in the same transaction.
  `HoldSweepService`'s existing Javadoc says the order of those two statements is load-bearing —
  keep that true and keep the comment accurate.
- No regression in `HoldLockOrderDeadlockIntegrationTest`, `HoldReleaseSeatLockRaceIntegrationTest`,
  `NoOversellIntegrationTest`, or `HoldRedisUnavailableRaceIntegrationTest`.
- Full `./mvnw test` green.

## Relevant conventions
- **ADR-0010** — no unlocked entity reads before a row lock. Constrains how the ids may be gathered;
  scalar projection only.
- **ADR-0011** — `event_seats` is locked before `holds` everywhere. Must survive unchanged.
- **ADR-0002** — lazy expiry is authoritative; the sweep is UX-only reconciliation, so its
  behaviour must stay unchanged.
- **ADR-0001** — Postgres is the concurrency authority; a deadlock-induced 500 on a valid request
  is a direct failure of that guarantee's usability.
- CLAUDE.md: explicit `@Transactional`; repository queries carry Javadoc explaining *why* a
  projection is a projection (see the two existing ones).
