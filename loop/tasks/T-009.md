# T-009 — Document the 401 that T-008 made reachable on the two booking reads
Milestone: M7 (#12)   Status: pending

## Description
T-008 added `authenticated()` carve-outs so `GET /api/bookings/me` and `GET /api/bookings/{id}`
return 401 to anonymous callers instead of 500. It did not update those two operations'
`@ApiResponse` sets, so the OpenAPI document still says neither can return 401.

Three of `BookingController`'s five operations declare `responseCode = "401"`. The two that do
not are exactly the two T-008 just made return it.

**The irony worth noting:** `OpenApiDocumentationTest` asserts each operation's status set
**exactly** rather than as a superset — precisely so documentation drift fails loudly. But T-008
changed the behaviour without touching either the annotations or the test's expectations, so the
test now pins the wrong set in place and passes. An exact-match assertion only helps when the
expectation is updated alongside the behaviour; here it silently ratified the drift instead.

## Acceptance criteria
- `GET /api/bookings/me` and `GET /api/bookings/{id}` declare `401` with the `UNAUTHENTICATED`
  `ErrorResponse` example, matching how the other three booking operations already document it.
- `OpenApiDocumentationTest`'s expected status sets for both operations are updated to include
  `401`, and the suite is green.
- Sweep the other five controllers for the same gap: any operation carrying
  `@SecurityRequirement(name = "bearerAuth")` can return 401, so it should document it. Check
  `HoldController` and `AuthController`'s `me` in particular. Fix any found, or state that none
  were.

## Also worth fixing while here (small, found alongside)
- `SecurityConfig`'s class Javadoc still opens by saying "`/api/auth/register` and `/api/auth/login`
  plus any `GET /api/**` request are currently public." That is now imprecise — three GETs are
  carved out. The following sentence does list the exceptions, so the paragraph is not wrong
  overall, but the opening clause reads as stale. Tighten it.
- `OpenApiDocumentationTest.userScopedBookingReadsDeclareBearerAuthDespiteBeingUserScopedGets` is
  a stale name. The "despite" originally meant "despite `SecurityConfig` not enforcing it" — which
  T-008 fixed — and as written it now parses as "user-scoped reads … despite being user-scoped
  gets," which says nothing. Rename to reflect what it asserts today.

## Known residual — consider whether to address or record
T-008's general guardrail (`everyDeclaredBearerAuthOperationRejectsAnonymousRequestsWith401`)
catches an operation that **declares** `bearerAuth` but lacks a matcher carve-out. It cannot catch
a newly added user-scoped endpoint that is missing *both* the annotation and the carve-out —
nothing would flag it as user-scoped in the first place. That is a narrower gap than the one T-008
closed, and possibly acceptable, but it is the residual path by which this bug class recurs.
Assess whether it is worth closing (and how) or worth recording as accepted.

## Relevant conventions
- ADR-0004 (auth boundary is response-identity dependence, not HTTP verb).
- ADR-0009 (error codes are a closed enum) — the 401 body uses `UNAUTHENTICATED`.
- T-005's depth (b) convention: one `ErrorResponse` example per documented status; derive each
  operation's status set from what it can really return, never from a boilerplate block.
