# T-008 — Booking read endpoints are reachable anonymously (ADR-0004 violation)
Milestone: M7 (#12)   Status: pending

## Description
`GET /api/bookings/me` and `GET /api/bookings/{id}` are user-scoped — their entire response
depends on who is asking — but neither requires authentication. `SecurityConfig`'s matchers are
first-match-wins:

```java
.requestMatchers(HttpMethod.GET, "/api/auth/me").authenticated()   // line 55 — the one carve-out
.requestMatchers(HttpMethod.POST, "/api/auth/register", "/api/auth/login").permitAll()
.requestMatchers(HttpMethod.GET, "/api/**").permitAll()            // line 57 — catches both booking reads
.requestMatchers("/v3/api-docs/**", "/swagger-ui/**", "/swagger-ui.html").permitAll()
.anyRequest().authenticated()
```

Both booking reads fall through to the blanket `GET /api/**` permitAll at line 57. Spring Security
admits the anonymous request with no `Authentication` populated, `@AuthenticationPrincipal
AuthenticatedUser principal` resolves to `null`, and `principal.id()` throws an NPE that
`GlobalExceptionHandler`'s catch-all converts into a **500**.

**Verified empirically** during T-005 with a throwaway MockMvc probe (since deleted): anonymous
requests to both endpoints return 500, not 401.

**This is an ADR-0004 violation, not a documentation gap.** That ADR's rule is that a route is
public if and only if its response does not depend on who is asking. These two depend on nothing
else.

**`SecurityConfig`'s own Javadoc predicted this exact bug** (lines ~33-37):

> Any future user-scoped GET (e.g. "my bookings") must get the same explicit carve-out,
> registered before the blanket GET rule — matcher order is first-match-wins.

M6 then added "my bookings" without the carve-out. The instruction was written down and not
followed, which is worth noting in `/retro` — a comment is a weak enforcement mechanism for an
invariant that a test could have pinned.

## Severity
**No information is disclosed today.** `principal.id()` NPEs before any repository call, so no
booking data reaches an anonymous caller — the failure is a 500, not a leak. But:
- the auth boundary is not enforced, so it holds by accident of a null dereference rather than by
  configuration;
- any future change making the controller tolerant of a null principal (a defaulted user, an
  optional principal, a null-safe rewrite) would silently convert this into a real data leak;
- a 500 on an unauthenticated request is itself wrong — it should be 401.

Treat it as a genuine security defect to fix promptly, not an emergency.

## Acceptance criteria
- `GET /api/bookings/me` and `GET /api/bookings/{id}` require authentication, via explicit
  `authenticated()` matchers registered **ahead of** the blanket `GET /api/**` rule at line 57,
  mirroring how `GET /api/auth/me` is carved out at line 55.
- An anonymous request to either returns **401 with the `UNAUTHENTICATED` `ErrorResponse` body**
  produced by `SecurityConfig`'s `authenticationEntryPoint` — not 500, not 403, not an empty body.
- **A test pins the boundary rather than trusting the comment.** This is the important part: the
  existing Javadoc instruction was already there and did not prevent the bug. Prefer a test that
  is hard to leave stale — e.g. one asserting that every user-scoped route is authenticated,
  written so a newly added user-scoped endpoint fails it by default rather than silently passing.
  If a fully general form is impractical, an explicit per-route test is acceptable, but say why.
- Authenticated behaviour is unchanged: both endpoints keep working exactly as they do now, and
  ADR-0008's 404-not-403 semantics on ownership mismatch are untouched.
- T-005's `OpenApiDocumentationTest` already asserts `bearerAuth` is documented on both operations
  — after this fix, documentation and enforcement finally agree. Check whether that test's comment
  about the mismatch needs updating, and update `BookingController`'s class Javadoc, which
  currently documents the gap as a known issue.
- Full `./mvnw test` green.

## Consider while you are here
Whether the blanket `GET /api/**` permitAll is still the right default at all. Its Javadoc calls
it "a placeholder standing in for catalog/browse endpoints M3 hasn't introduced yet." Those now
exist (venues, events, event seats), so the placeholder could be replaced by explicit permitAll
matchers for exactly those three public read families, making the default deny rather than allow.
That would prevent this whole class of bug rather than patching one instance. It is a larger
change and may deserve its own task and an ADR amendment — assess and recommend, do not
unilaterally expand scope.

## Relevant conventions
- ADR-0004 (auth boundary is response-identity dependence, not HTTP verb) — the governing rule.
- ADR-0008 (404 not 403 on ownership mismatch) — must survive unchanged.
- ADR-0009 / `ErrorCode` — the 401 body uses `UNAUTHENTICATED`, already in the enum.
- CLAUDE.md: no ad hoc error responses; `SecurityConfig`'s entry point already builds the shared
  `ErrorResponse` shape.
