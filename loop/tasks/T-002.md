# T-002 — Booking/confirm-stage load: declines and shared-hold races
Milestone: M7 (#12)   Status: pending

## Description
T-001 proves no oversell but puts contention only on the hold stage. This task loads the two
later stages, where a double-charge or double-release would actually hide.

**Method 1 — all-decline under load.** 4 seats, 8 threads running the full pipeline with
`SimulatedPaymentServiceImpl.forceNextOutcome(FAILED)`. A declined payment sets the booking
`FAILED` and calls `releaseBookingSeats`, flipping seats back to `AVAILABLE` mid-race — the
most interesting transition in the pipeline and currently untouched by any concurrency test.
Assert every seat ends `AVAILABLE`, every booking ends `FAILED`, and no seat is stranded
`BOOKED` or `HELD`. This is the mirror of T-001's happy-path invariant.

**Method 2 — shared-hold booking + confirm race.** One hold covering 4 seats, then 8 threads
all racing `POST /api/bookings` on that same hold id, and every thread that gets a booking id
racing `POST /api/bookings/{id}/confirm`. This is genuine multi-stage contention: the `Booking`
row lock and the payment idempotency path both come under real load. Exactly one booking must
be created, `SimulatedPaymentServiceImpl.invocationCount()` must be exactly 1, and all 4 seats
must end `BOOKED` under that single booking.

**The forced outcome is process-wide.** `SimulatedPaymentServiceImpl` is a singleton whose
`forcedOutcome` and `invocationCount` are shared across all threads, so a run declines for
everyone or no one — mixed outcomes are not achievable without changing production code, and
aren't worth it. Reset both in `@AfterEach`, exactly as `BookingIntegrationTest#tearDown` does;
`invocationCount` in particular is global and will corrupt Method 2's assertion if a previous
test leaked into it.

Same fixture discipline as T-001: private Venue/Event/Seats in `@BeforeEach`, far-future
`startsAt`, not `@Transactional`.

## Acceptance criteria
- Full `./mvnw test` green and stable across repeated runs; whole-suite budget ~3 minutes.
- Method 1: all 4 seats `AVAILABLE`, all bookings `FAILED`, all payments `FAILED`, no seat left
  `BOOKED` or `HELD`, no 500s.
- Method 2: exactly one `Booking` row exists for the hold; `invocationCount() == 1` (proving no
  double-charge); all 4 seats `BOOKED`; losing threads get a non-500 domain error; the hold ends
  `CONVERTED`.
- No thread receives a 500 in either method.
- Assertions run from a fresh transactional read after all threads join.
- Both methods' Javadoc states which stage's contention they cover, so the split of
  responsibility with T-001 is legible without reading both files.
