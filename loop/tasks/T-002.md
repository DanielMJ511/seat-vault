# T-002 — GET /api/bookings/{id} and list-mine read endpoints

Milestone: M6 (#11)   Status: pending

## Description

Add two read-only endpoints to `BookingController` (`src/main/java/com/seatvault/seat_vault/controller/BookingController.java`):

1. `GET /api/bookings/{id}` — detail view of a single booking, scoped to the caller (`@AuthenticationPrincipal AuthenticatedUser principal`), reusing the existing `BookingResponse` DTO and `toResponse(...)` mapping already used by `create`/`confirm`.
2. `GET /api/bookings/me` — list of the caller's own bookings, returning `List<BookingResponse>` (full DTO reused as-is per grilling decision, no summary DTO).

Add a corresponding read method to `BookingService` (e.g. `getBooking(userId, bookingId)`, `listBookings(userId)`) following the same ownership-check pattern as `confirmPayment`/`cancel`: 404 for not-found-or-not-owned, per ADR-0008 — no 403 path.

## Acceptance criteria

- `GET /api/bookings/{id}` for the caller's own booking returns 200 with the full `BookingResponse`.
- `GET /api/bookings/{id}` for a nonexistent or not-owned booking returns 404.
- `GET /api/bookings/me` returns only the caller's own bookings, each as a full `BookingResponse`.

## Relevant conventions

- DTOs only, never `@Entity` in the response — reuse `BookingResponse`/`BookingSeatResponse`/`PaymentResponse`, no new DTO needed.
- Controllers call Services only, never Repositories.
- ADR-0008: ownership mismatch on `GET /api/bookings/{id}` returns 404, matching `confirmPayment`'s existing behavior — not 403.

## Files likely touched

- `src/main/java/com/seatvault/seat_vault/controller/BookingController.java`
- `src/main/java/com/seatvault/seat_vault/service/BookingService.java`
- Possibly a new DTO record if grilling decided a summary shape is needed for the list view
