# T-002 — Decoupled fail-fast readiness for a Postgres outage
Milestone: M9 (#22)   Status: pending
Closes: #20
Depends on: T-001 (a gated scheduler is what makes this task's `mvn test` verification meaningful)

## Description

`/actuator/health/readiness` hangs instead of fast-failing when Postgres is unreachable. Found in
M8/T-004 while verifying the container `HEALTHCHECK` against a real running stack: with
`docker stop seatvault-postgres` and the app still running, a direct request returned **nothing at
all** within a 15-second client timeout.

The mechanism: Actuator's `DataSourceHealthIndicator` acquires a real pooled connection to validate
the datasource, and `application.properties` does not override HikariCP's default 30s
`connection-timeout`. So during an outage the indicator blocks for up to 30s per call.

**Nothing is currently broken and this is not a regression.** The container healthcheck added in
T-004 stays correctly bounded, because `wget --timeout=3s` (`Dockerfile:54`) cuts each probe off long
before the app-side 30s could elapse; the container transitions `healthy → unhealthy` at a
well-bounded ~35s, verified.

Two consequences make it worth fixing anyway, and they are not equally weighted:

1. **Weaker: any prober that isn't ours hangs.** An ALB target group, a Kubernetes readiness probe,
   or a human with `curl` gets a 30s stall instead of a fast, informative 503. Ours is bounded only
   because we happened to set a 3s timeout on it. (Note when weighing this: k8s and ALB probes carry
   their own timeouts and read one as a failure anyway, so the practical damage here is diagnostic
   confusion rather than a wrong verdict.)
2. **This is the one that earns the fix: it competes for the pool during exactly the wrong moment.**
   HikariCP's pool is small (default 10; `application-test.properties` raises it to 30 for tests
   only). During a genuine Postgres outage, real user requests are already blocking on connection
   acquisition — and the readiness probe adds another consumer to that queue every 10 seconds, each
   holding a request thread for its full 30s wait. That is a thread- and connection-exhaustion
   amplifier on a system whose entire design claim is behaviour under contention.

## SETTLED — do not re-decide

**Decouple the health check's connection path; do not set a global
`spring.datasource.hikari.connection-timeout`.**

#20's literal deliverable was the global property. It is the risky version, and the issue itself
hints at the better path ("consider whether the health indicator's timeout should be decoupled").
The reason: that property is **global** — it applies to real user requests, not just the health
probe. This app blocks threads on `findByIdForUpdate` with *no lock timeout*, so a thread waiting a
while for a connection is normal and healthy under legitimate peak contention. A short global value
converts that queueing into spurious 500s — exactly the false defect `application-test.properties`
raised `maximum-pool-size` to 30 to avoid, and exactly what `NoOversellIntegrationTest` and
`BookingConfirmLoadIntegrationTest` exist to treat as real.

Leave the application pool's `connection-timeout` at its default. Register a custom `db`
`HealthIndicator` backed by its own short-timeout connection path, so readiness fails fast **without
changing how real requests queue.**

**Readiness group membership does not change.** `management.endpoint.health.group.readiness.include`
stays `readinessState,db`. Per ADR-0013, Postgres is fatal to readiness and Redis is not; this task
is about *how promptly* that fatality is reported, never whether it should be.

## Approach — SETTLED by grilling (2026-08-17). Recorded as **ADR-0014** — read it first.

**Readiness means "can this instance reach Postgres."** Pool saturation is deliberately excluded: it
is a load signal, and an instance struggling under contention is one you must *not* evict, since
shedding it pushes load onto its siblings. Same argument ADR-0013 used to keep Redis out.

Four facts from grilling constrain the implementation. All were verified with `javap -v` against the
actual jars, not reasoned from our source — do not re-derive them by reading Spring's docs:

1. **It must not be a `DataSource` bean.** `DataSourceAutoConfiguration$PooledDataSourceConfiguration`
   carries `@ConditionalOnMissingBean({DataSource.class, XADataSource.class})`, so registering any
   `DataSource` bean **suppresses Boot's application datasource entirely** — a silent, catastrophic
   takeover. `DataSourceHealthContributorAutoConfiguration` separately composes
   `Map<String, DataSource>`, so a second one would also be folded into a composite `db` indicator.
2. **The seam is the bean name.** That health autoconfiguration backs off on
   `@ConditionalOnMissingBean(name = {"dbHealthIndicator", "dbHealthContributor"})`. A bean named
   **`dbHealthIndicator`** replaces Boot's cleanly and still resolves as `db` in the readiness group.
3. **`JdbcConnectionDetails` is always present** — `PooledDataSourceConfiguration` declares a
   `PropertiesJdbcConnectionDetails` fallback `@ConditionalOnMissingBean(JdbcConnectionDetails.class)`
   — so it reflects the Testcontainers target in tests and the configured one otherwise. Derive the
   probe target from it, not from `spring.datasource.*` properties (which do **not** carry the
   container URL under `@ServiceConnection`). Note it lives *inside* `PooledDataSourceConfiguration`,
   so it disappears too if fact 1 is violated.
4. **pgjdbc timeouts are integer seconds.** `connectTimeout` (default 10), `socketTimeout` (default
   0 = infinite) and `loginTimeout` (default 0) are all parsed with `Integer.parseInt`. One second is
   the floor; there is no sub-second granularity.

### Settled implementation

- **`DriverManager`, fresh connection per probe.** Pooling would defeat the semantics — a cached idle
  connection can answer UP at a moment when no *new* connection can be established, which is exactly
  the failure being probed for. One TCP connect every 10s is not worth optimising against
  correctness. *Rejected:* `PGSimpleDataSource` (would need the driver promoted from `runtime` scope
  and names the vendor in main source) and a non-bean `HikariDataSource` (lifecycle for one
  connection).
- **Run `SELECT 1`**, not connect-and-close. A server completing TCP and auth but unable to serve —
  in recovery, or out of WAL disk — must not report UP; connect-only would say it does, making this
  replacement strictly weaker than the Boot indicator it replaces. `socketTimeout` is what bounds
  that read.
- **`connectTimeout=2`, `socketTimeout=2`, `loginTimeout=3`**, putting the worst case near five
  seconds. **Widen the `Dockerfile` HEALTHCHECK from `--timeout=3s` to `--timeout=6s`** to match.
  Leaving it at 3s would have our own probe silence the prompt 503 this task exists to produce —
  reproducing the original opacity at smaller scale. 6s stays well under the 10s interval, so probes
  never overlap and the `healthy → unhealthy` transition timing is unchanged.
- Note the asymmetry that makes these values cheap: a **refused** connection fails instantly whatever
  they are. They only bite on a blackholed host where packets are dropped without an RST.

**Rejected: a pool-saturation indicator.** Real observability, but it answers an operator's question,
not an orchestrator's, and adding it under cover of this fix would be scope decided by momentum.

Put the reasoning where the related reasoning already lives: `application.properties`'s Actuator
block already documents readiness composition (ADR-0012, ADR-0013) at length, and
`application-test.properties` already documents the `maximum-pool-size` decision this one is in
tension with. Follow that comment style.

## Acceptance criteria

1. **With Postgres unreachable, `GET /actuator/health/readiness` returns a prompt 503** rather than
   hanging — asserted against an actual elapsed-time bound, since "prompt" is the whole deliverable
   and an untimed assertion would pass just as well against the 30s hang.
2. **Full `./mvnw test` green**, with particular attention to `NoOversellIntegrationTest` and
   `BookingConfirmLoadIntegrationTest`. A too-short value surfaces there as spurious 500s — which is
   exactly what those tests exist to treat as defects, so do not relax them to accommodate a number.
3. The container healthcheck still transitions to `unhealthy` on a Postgres outage and recovers
   afterwards (M8/T-004 observed ~35s and ~12s) — re-verified after widening `--timeout` to 6s.

**Method note for the timeout values, flagged as unverified.** `docker stop` produces a *refused*
connection, so it exercises the DOWN path but not `connectTimeout`/`loginTimeout`. `docker pause`
may produce the dropped-packet hang that would actually exercise them. Try it — but **confirm by
observation rather than assuming it behaves that way**, and if it does not, report the gap honestly
instead of claiming coverage the run did not produce.

## This is testable in-process now — M8's retro said to check for exactly this

M8's grilling concluded that "Postgres fatal to readiness" could not be proven from the test suite,
because the Spring context cannot boot without a database, and settled for asserting group
*composition*. The retro's lesson was: **"untestable" almost always means "untestable at the layer I
was thinking about."**

**Decoupling changes that layer.** With a separate health connection path, a test config can point
*only the health path* at a dead port while the main datasource stays on the real Testcontainers
Postgres. The context boots normally (Flyway and JPA use the real one), and readiness can be observed
failing in-process — no container stack required.

**The seam (settled):** the indicator takes its target from a small injectable component that
defaults to deriving from `JdbcConnectionDetails`; a `@TestConfiguration` supplies a dead-port
replacement of that component. *Rejected:* an override property such as `management.health.db.url`,
because that is a production knob existing only for tests. Note why the seam is necessary at all — if
the indicator read the shared `JdbcConnectionDetails` bean directly, overriding it in a test would
redirect the **main** datasource too, and the context would not boot. That is the wall M8 hit.

`BrokenRedisTestConfig` is the exact model to copy: a `@TestConfiguration` supplying a component
pointed at a dead local port, imported alongside `PostgresTestcontainersConfig`, with Javadoc
explaining the dead-port choice and the context-cache cost.
`HealthReadinessRedisDownIntegrationTest` is the model for the assertions.

### State honestly what this proves — the scope is narrower than it looks

**Refused case only (settled).** A dead port produces a *refused* connection, which fails instantly
regardless of what the timeouts are set to. So this test proves the fail-fast **mechanism** and the
decoupling (the context boots on a real database while readiness reports DOWN). It proves **nothing
about the timeout values** in the Approach section — those only bite on a blackholed host. Assert a
loose elapsed-time upper bound to prove *no hang*, and do not dress it up as proving the numbers.

**Rejected: a blackhole test** against a reserved non-routable address (RFC 5737 `192.0.2.1`,
`10.255.255.1`). Whether such an address drops or returns an immediate RST depends on the host
routing table, the Docker bridge and the CI provider's egress — it would pass locally and behave
differently in CI. That is precisely the environment-sensitive flake M9 exists to remove; trading one
for another would be a poor bargain. Document the gap instead.

It also does not prove the health path and the application datasource point at the same database —
that is a wiring property, observable only at the container layer (criterion 3). Say all of this in
the Javadoc rather than letting the test read as broader coverage than it is.

## Relevant conventions
- CLAUDE.md: constructor injection, no `@Autowired` fields; DTOs are records; services throw
  `ApiException`. A `HealthIndicator` is infrastructure, not a controller — it does not route
  through `GlobalExceptionHandler`.
- **ADR-0014** — this task's own decision record. Read it before starting; it carries the reasoning
  the code comments should not restate at length.
- **ADR-0013** — Redis cannot fail readiness; Postgres is deliberately fatal to it. Unchanged here,
  but **amended** by ADR-0014: its claim that Postgres-down cannot be tested the way Redis-down is
  held only while the health check shared the application datasource.
- **ADR-0012** — Actuator exposure is an allowlist on the shared chain. `SecurityConfig:107`
  `permitAll`s the two group paths route by route. **Do not add a matcher** — the deny-by-default
  shape is the mechanism, and the existing comment says so explicitly.
- **ADR-0001** — Postgres is the concurrency authority, which is why pool pressure during an outage
  is correctness-adjacent rather than cosmetic.

## Warning carried from M8/T-003
Boot substitutes a **synthetic probe group** whose `showComponents()`/`showDetails()` compile to
hardcoded `false`, silently ignoring the properties you set, unless a group is explicitly declared
under `management.endpoint.health.group.<name>.*`. That cost a task in M8 and was only settled by
`javap -c` on the framework jar. **Confirm the custom indicator actually lands in the readiness group
by observation, not by reading config.**

More generally: a claim about how Spring, Hikari, or the Postgres driver behaves internally is a
hypothesis until observed, and reading our own code cannot settle it. Applies directly to
`loginTimeout` vs `socketTimeout` vs `connectTimeout` semantics — probe them, do not reason about
them.
