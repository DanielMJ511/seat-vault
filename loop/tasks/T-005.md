# T-005 — OpenAPI operation/response examples across the API surface
Milestone: M7 (#12)   Status: pending

## Description
**Depends on T-004** — the `@ApiResponse` examples cite `ErrorCode` constants that T-004
creates. Do not start until it's merged.

springdoc (`springdoc-openapi-starter-webmvc-ui` 3.1.0) is already on the classpath and
`OpenApiConfig` registers a `bearerAuth` security scheme — but that is the *only* OpenAPI
annotation in the codebase, and **nothing references the scheme**, so today Swagger UI shows an
Authorize button that applies to no operation. Every endpoint is documented by springdoc's
reflection defaults alone: no summaries, no error responses, no examples. Issue #12's
verification step is a manual Swagger UI smoke test, which only means something once the
generated document actually describes the API.

Annotate all six controllers (`AuthController`, `VenueController`, `EventController`,
`EventSeatController`, `HoldController`, `BookingController`) at **depth (b)**:
- `@Operation` summary per endpoint
- `@SecurityRequirement(name = "bearerAuth")` on protected operations
- `@ApiResponse` per status that endpoint can actually return, each carrying one
  `ErrorResponse` example

Not depth (c): no per-field `@Schema` descriptions across the 14 DTOs — that's annotation noise
for little added clarity.

**The generated document is the consumer-facing catalogue.** There is deliberately no
hand-maintained Markdown table of error codes: descriptions live on the `ErrorCode` constants
from T-004 and surface through these annotations, so the list cannot drift from the code.
Reference the enum constants wherever the annotation API permits constant expressions rather
than retyping literals.

**Which operations are protected is not a guess.** Read `SecurityConfig` — `POST
/api/auth/register` and `/login` plus any `GET /api/**` are currently public, with `GET
/api/auth/me` carved out as authenticated. Note that `GET /api/bookings/me` and `GET
/api/bookings/{id}` are user-scoped but fall under the blanket public-GET rule; ADR-0004 says a
route is public iff its response doesn't depend on who's asking, so **flag any mismatch you
find rather than silently annotating around it** — that would be a real security finding, not a
docs problem.

## Acceptance criteria
- `/v3/api-docs` renders without error; every endpoint carries a summary and its real set of
  response statuses.
- A test asserts this rather than relying on manual inspection — fetch `/v3/api-docs` via
  MockMvc and assert operation/response presence for a representative sample of paths.
- Protected operations declare `bearerAuth`; genuinely public ones do not.
- Error examples cite codes that exist in T-004's enum.
- **Booking endpoints document 404, not 403, for ownership mismatch** (ADR-0008). Docs that
  contradict the implementation here would be worse than no docs.
- Swagger UI at `/swagger-ui.html` supports the issue's manual smoke test end to end: authorize
  with a JWT, then run register → login → hold → book → confirm → cancel from the UI.
- No production behavior change — annotations only. Full `./mvnw test` green.

## Relevant conventions
- ADR-0004 (auth boundary is response-identity dependence, not HTTP verb) — determines which
  operations get `bearerAuth`. Follow the ADR, not a GET/POST heuristic.
- ADR-0008 (404 not 403 on ownership mismatch) — the documented booking responses must match.
- ADR-0009 (error codes are a closed enum) — the source of every code and description used here.
- ADR-0005 (JWT stateless and non-revocable), ADR-0006 (EventSeat id is the API-level seat
  reference) — relevant to operation descriptions.
- CLAUDE.md: DTOs are `record`s and `@Entity` objects are never exposed. If an annotation would
  document an entity as a response body, that's a bug in the annotation.
- CLAUDE.md: controllers stay thin — annotations must not smuggle logic in.
