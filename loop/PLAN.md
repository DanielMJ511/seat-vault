## Decisions from grilling (2026-08-13)

### Concurrency suites (T-001, T-002)
- **Two race shapes, not one.** Issue #12's stated invariant `booked_count == seat_count` only
  holds for single-seat-per-thread. With overlapping multi-seat holds, all-or-nothing rollback
  means a seat can end AVAILABLE because everyone who wanted it also wanted something they
  couldn't get. Both shapes are covered, with the honest invariant for each: exact equality for
  round-robin, and "no seat in two bookings, no deadlock, no 500" for the overlapping shape.
- **Correction (2026-08-14, from T-001's code review).** Grilling assumed T-001's overlapping
  shape would exercise `HoldService`'s ascending-id Postgres lock ordering. It cannot:
  `createHold` acquires all of a request's Redis locks (non-blocking `SETNX`) before any
  Postgres work, so while Redis is up a thread with an overlapping seat set is rejected at the
  Redis tier and never reaches `findByIdForUpdate` — the ordering loop only ever runs
  uncontended. That path is reachable **only with Redis down**, where `tryLock` fail-opens for
  everyone and all threads enter Postgres at once, so the coverage moved to **T-003 (Race 2)**.
  T-001's shape (b) also widened from 5 seats to 8, so that disjoint requests can win
  concurrently — which is a real invariant shape (a) cannot produce, and its actual purpose.
- **Contention in T-001 bites only at the hold stage.** Holds are single-owner by construction,
  so a thread that wins its hold books and confirms unopposed. This is a real limitation of the
  pipeline shape, not an oversight — T-002 exists to put genuine load on stages 2 and 3 via a
  hold shared across threads.
- **Scale:** 5 seats/20 threads (round-robin), 8 seats/12 threads × 3 overlapping seats
  (widened from 5 — see the correction above), 4 seats/8 threads (declines), 4 seats/8 threads
  (shared hold).
- **`spring.datasource.hikari.maximum-pool-size=30` in `application-test.properties`.** HikariCP
  defaults to 10 connections and `findByIdForUpdate` has no lock timeout, so a thread blocked on
  a row lock holds its connection. Past ~10 threads the suite would measure connection starvation
  rather than Postgres locking, and Hikari's 30s acquisition timeout would surface as a 500 —
  which these tests are supposed to treat as a defect.
- **Payment declines are all-or-nothing.** `SimulatedPaymentServiceImpl` is a singleton whose
  `forcedOutcome`/`invocationCount` are process-wide, so a run declines for every thread or none.
  Mixed outcomes would require changing production code and aren't worth it.
- Everything stays in the default `mvn test` (no `@Tag` exclusion) against a ~3-minute whole-suite
  budget. A concurrency test excluded by default is one nobody runs.

### Redis fallback (T-003)
- **Two mechanisms for two jobs:** a `@TestConfiguration` `RedisConnectionFactory` pointed at a
  dead port for the end-to-end race (real `DataAccessException`s through the real Spring Data
  Redis stack, contained to one context), and a throwing stub for the isolated `RedisLockService`
  assertions (where the point is observing the *absence* of a call). Stopping the shared
  Testcontainers Redis was rejected — it breaks every later test in the cached context.
- **Hold-stage races, not the full pipeline.** The claim is narrow ("Postgres alone still
  serializes seat acquisition") and a hold-stage assertion proves it; re-running the pipeline
  would mostly re-test T-001 in a second context against the runtime budget.
- **Two races, per the 2026-08-14 correction above.** Race 1 is the single-seat fallback proof
  (exactly one winner). Race 2 is an overlapping multi-seat race — the suite's *only* coverage
  of `HoldService`'s ascending-id Postgres lock ordering, reachable nowhere else because Redis
  gates overlapping requests before they reach Postgres whenever it is up.

### Error-code catalogue (T-004) — formalized as ADR-0009
- Closed `ErrorCode` enum carrying HTTP status and description; raw-string `ApiException`
  constructors removed so there's no bypass. No separate drift test is needed — the compiler
  enforces structurally what a test would otherwise assert.
- **The catalogue is 21 codes, not 19.** `UNAUTHENTICATED` and `ACCESS_DENIED` are written
  directly by `SecurityConfig`, bypassing `GlobalExceptionHandler` entirely; both join the enum.
  `ACCESS_DENIED` is unreachable today (no rule uses `hasRole`/`hasAuthority`) and stays anyway.
- **Split test: does the client's next action differ?** `HOLD_EXPIRED` splits out, keyed on
  domain state rather than throw site, so a timed-out hold returns the same code whether or not
  `HoldSweepService` has run. `SEAT_ALREADY_HELD` stays merged across its Redis and Postgres
  paths — identical client action, and the merge is what makes ADR-0001 falsifiable in T-003.
- Needs a small Hold-level expiry helper mirroring `EventSeatAvailability`'s static-utility
  precedent (that class operates on `EventSeat` and can't answer this question).

### OpenAPI (T-005)
- Depth (b): `@Operation` summaries + `@SecurityRequirement` + `@ApiResponse` per real status with
  one `ErrorResponse` example each. Not per-field `@Schema` — annotation noise on 14 DTOs.
- **The generated document is the consumer-facing catalogue.** No hand-maintained Markdown table:
  descriptions live on the enum constants and surface through the annotations, so the list cannot
  drift from the code.
