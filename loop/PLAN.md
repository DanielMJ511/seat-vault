## Decisions from grilling (2026-08-13)
- List route: `GET /api/bookings/me` (stays under the existing controller base path).
- Ownership mismatch: 404 for both "not found" and "not owned," across every Booking endpoint (detail, list, cancel) — formalized as ADR-0008, generalizing the convention `confirmPayment` already followed implicitly.
- List response: reuses the full `BookingResponse` as-is (seats + payment nested) — no separate summary DTO.
- Hold: `createFromHold` already sets `Hold.status = CONVERTED` at booking-creation time, so cancel never touches the Hold record.
- Payment: cancel never touches the Payment record — already an explicit non-goal in `CONTEXT.md` ("stays SUCCEEDED... no Refund concept exists").
- Isolation: cancel uses a bare `@Transactional` + pessimistic row lock via `findByIdForUpdate`, matching `confirmPayment` exactly — no explicit isolation level.
- Concurrency: the only real race is double-cancel (two concurrent cancel calls on the same CONFIRMED booking), not cancel-vs-confirm (their preconditions — CONFIRMED vs PENDING — never overlap). The row lock resolves it the same way `confirmPayment`'s idempotency already does: first commits, second sees `CANCELLED` and gets 409.
