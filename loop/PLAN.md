## Two corrections to the source issues, carried into the packets

1. **#21 names two tests to revisit; there are three.** `HoldReleaseSeatLockRaceIntegrationTest` also justifies its PID-scoped `pg_locks` poll by citing the ungated scheduler. M8's own retro lesson — *a fact worth stating twice will drift, so grep for every instance when correcting one* — applies to the issue that came out of that retro.
2. **#20's literal deliverable is the risky version.** `spring.datasource.hikari.connection-timeout` is global: it applies to real user requests, not just the health probe. This app blocks threads on `findByIdForUpdate` with no lock timeout, so a short global value converts legitimate peak-contention queueing into spurious 500s — exactly the false defect `application-test.properties` raised `maximum-pool-size` to 30 to avoid. Take the decoupled path #20 itself hints at; leave the application pool's timeout at its default.

## Decisions from grilling

Grilled on 2026-08-17. Frontier resolved to empty; the packets carry these as SETTLED sections.

### Facts established by observation (not from our source)
- `DataSourceAutoConfiguration$PooledDataSourceConfiguration` carries `@ConditionalOnMissingBean({DataSource.class, XADataSource.class})` — **registering any `DataSource` bean suppresses Boot's application datasource entirely.** Verified with `javap -v` on `spring-boot-jdbc-4.1.0.jar`.
- `DataSourceHealthContributorAutoConfiguration` backs off on `@ConditionalOnMissingBean(name = {"dbHealthIndicator", "dbHealthContributor"})` and otherwise composes `Map<String, DataSource>`. The bean *name* is the replacement seam.
- A `JdbcConnectionDetails` bean is always present — `PooledDataSourceConfiguration` declares a `PropertiesJdbcConnectionDetails` fallback `@ConditionalOnMissingBean(JdbcConnectionDetails.class)` — so it reflects the Testcontainers target in tests and the configured one otherwise. It lives *inside* that class, so it also disappears if we define a `DataSource` bean.
- pgjdbc's `connectTimeout` (default 10), `socketTimeout` (default 0) and `loginTimeout` (default 0) are **integer seconds**, parsed with `Integer.parseInt`. One second is the floor; there is no sub-second granularity. Verified in `PGProperty` bytecode.
- `JwtProperties.validate()` throws unless `dev` or `test` is active, so **no-profile contexts cannot boot in tests.**
- `HoldSweepService#sweepExpiredHolds` is the only `@Scheduled` method in main.
- `CONTEXT.md` carries no operational vocabulary and needs no change — M9 introduces no domain terms.

### T-001
- **Property gate, not profile gate**: `@ConditionalOnProperty(name = "seatvault.sweep.scheduling.enabled", matchIfMissing = true)`. Rejected `@Profile("!test")` because it ties production reconciliation to a profile *name*, and "test" is exactly the kind of name a deployed staging environment gets — which would silently kill the sweep, the failure #21 explicitly calls worse than the flakiness it fixes.
- Default written **explicitly** as `=true` in `application.properties` so there is no invisible default; `matchIfMissing = true` is the backstop if that line is ever deleted. `=false` in `application-test.properties`.
- **OFF proof**: under `test`, assert no registered task targets `sweepExpiredHolds`.
- **ON proof**: a real `@SpringBootTest @ActiveProfiles("dev")` context with the property absent, so it falls through to `application.properties` and exercises the production value rather than a fixture. `ApplicationContextRunner` was rejected — it checks the condition, not a registered task.
- That `dev` context runs a live scheduler, which is what T-001 removes. **Accepted**, because the context is isolated (own cache key, own container, no siblings, no committed fixtures) so the shared-state hazard has nothing to act on. The Javadoc must state why isolation makes it safe and what would break the argument.

### T-002
- **Readiness = "can this instance reach Postgres."** Pool saturation is deliberately excluded: it is a load signal, and an instance struggling under contention is one you must not evict. Same argument ADR-0013 used for Redis. Recorded as ADR-0014.
- Bean named `dbHealthIndicator`; **never** a `DataSource` bean.
- `DriverManager`, fresh connection per probe — pooling would let a cached connection answer UP when new ones cannot be established. Rejected `PGSimpleDataSource` (needs the driver promoted from `runtime` scope) and a non-bean `HikariDataSource` (lifecycle for one connection).
- Target derived from `JdbcConnectionDetails` through an **injectable seam**, so a `@TestConfiguration` can point only the health path at a dead port — mirroring `BrokenRedisTestConfig`. Rejected an override property as a production knob existing only for tests.
- `SELECT 1`, not connect-and-close: a server that completes TCP and auth but cannot serve (recovery, WAL disk full) must not report UP.
- **`connectTimeout=2`, `socketTimeout=2`, `loginTimeout=3`**, and the `Dockerfile` healthcheck widened **3s → 6s**. Leaving it at 3s would have our own probe silence the 503 this task exists to produce. 6s stays under the 10s interval, so transition timing is unchanged.
- **In-process test covers the refused case only.** A blackhole test against a reserved non-routable address was rejected: whether it drops or refuses depends on the host routing table, Docker bridge and CI egress — an environment-sensitive flake, in a milestone whose purpose is removing them. The gap is documented rather than papered over.
- A pool-saturation indicator was considered and deliberately not built — real observability, but an operator's question, not an orchestrator's, and adding it here would be scope decided by momentum.
