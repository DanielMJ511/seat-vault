# LESSONS — retro-earned constraints

Cumulative across milestones. Only `/retro` writes here.

## Audience tags

Every lesson carries one or more audience tags. `/orchestrate` and `/plan-milestone` deliver each consumer only its own slice, so a lesson reaches the stage that can act on it and nowhere else:

- `[planning]` — `/plan-milestone`: task decomposition, packet contents, what to verify before a packet states it as fact.
- `[builder]` — `builder` and `implementer`: how to write the code and its tests.
- `[reviewer]` — `code-reviewer`: what to look for in a diff.
- `[docs]` — `docs-writer`: what must be true of a durable document (ADR, Javadoc, STATE entry).

A lesson with no tag is a bug in the entry, not a lesson for everyone. Add the tags it needs.

## Retired lessons

A lesson is **retired** when its content becomes permanent instruction text in a skill or agent file — at that point the copy here is duplication, and duplication drifts (see M8's third lesson, which is about exactly this). A retired lesson is replaced in place by a one-line pointer to where it now lives. It is never deleted outright: the pointer is what stops a future `/retro` from re-deriving the same lesson and re-adding it.

## M7 retro (2026-08-15)
- `[planning] [builder]` **Verify every factual claim in your task packet against the code before relying on it, and report discrepancies instead of working around them.** M7's packets were wrong four times: T-001 claimed a test shape exercised a Postgres lock-ordering path that Redis makes unreachable; T-004 claimed 21 error codes when there were 22 (the arithmetic omitted the code the task existed to add); T-006's exploit trace had a step the hold-row lock makes impossible; T-007 listed two lock-order offenders when there were three. Every one was caught by an agent that re-derived the claim — counting the enum itself, probing real Postgres — and every one would have shipped a wrong Javadoc, a wrong ADR, or an incomplete fix if taken on trust. Line numbers especially: they go stale the moment an earlier task edits the file.
- `[builder] [reviewer]` **A guard only counts if it can observe the failure it claims to catch — prove it by breaking the thing and watching the guard fire.** This failed three ways in M7. `SecurityConfig`'s Javadoc named "my bookings" as needing an auth carve-out and M6 shipped that exact endpoint without one, because a comment cannot fail a build. `OpenApiDocumentationTest` asserts response-status sets *exactly* so documentation drift fails loudly, yet missed T-008 entirely: the change moved the behaviour and touched neither the annotation nor the expectation, and an exact-match assertion is silent when both sides stay still. T-006's ownership guard was unreachable dead code until T-007's reordering made it live. By contrast, the two strongest deliverables of the milestone (T-006 and T-007) each ran their regression test against the *unfixed* code first and reported the failure output — do that whenever you add a guard.
- `[builder] [reviewer]` **Before writing a concurrency test, check that its parameters permit the outcome it asserts, and state in the Javadoc what it does not cover.** T-001's overlapping shape used 3-seat requests over a 5-seat pool, where any two requests must intersect, so only one thread could ever win — a costlier duplicate of the test beside it until the pool widened to 8. T-002's shared-hold race would have made `invocationCount() == 1` trivially true in a single pass, because only one thread ever receives a booking id; it needed two phases to become a real race. Assertions that cannot fail are worse than absent ones, because they read as coverage.
- `[builder] [reviewer]` **Judge locking by every row a transaction writes, not by where it calls `findByIdForUpdate`.** Both of M7's concurrency defects were invisible at the call site. In T-003 a plain `findAllById` pre-check loaded managed entities, so Hibernate's identity map served the later locked read from the pre-lock snapshot — the row lock was taken and its data ignored, and seats were genuinely double-booked. In T-007 nothing on the seats-first path asked for a hold lock at all; Hibernate took it when flushing a dirtied entity, producing an ABBA deadlock. See ADR-0010 and ADR-0011: before a locking loop the only safe reads of the type about to be locked are scalar projections and untouched lazy proxies, and lock order is about which table a transaction touches first by any means.
- `[planning] [builder]` **Sequence long tasks so the tree stays coherent at every step, and finish the fix and its regression test before the ADR or documentation.** Three agent runs in M7 were killed mid-task by API session limits and one stalled on a watchdog, twice leaving a task unverified. Work that lands fix-first survives an interruption; a half-applied refactor does not.

## M8 retro (2026-08-17)
- `[planning] [builder]` **A claim about how Postgres, Spring, or Micrometer behaves internally is a hypothesis until you observe it — and reading our own code cannot settle it.** This was M8's dominant failure mode, five times over, and every single resolution came from direct observation rather than reasoning: `pg_locks` records nothing for an *uncontested* row lock (it lives in the tuple's `xmax`), so a planned "assert it holds no lock" test was unobservable and needed `FOR UPDATE NOWAIT` from a third session instead; a `ctid` reordering lever calibrated on a 2-row table needed ~30 touches at 3000 rows because the tuple stays on the same heap page; Boot substitutes a synthetic probe group whose `showComponents()`/`showDetails()` compile to hardcoded `false` and silently ignores the properties you set, until a group is explicitly declared under `management.endpoint.health.group.<name>.*`; `DistributionSummary#max()` is a rolling `TimeWindowMax` that can *decrease*, not a cumulative value; and `StatusAggregator.getAggregateStatus(Set<Status>)` receives statuses with no component names, so the obvious way to make one indicator non-fatal does not exist. The techniques that settled these — `javap -c` on the framework jar, `EXPLAIN (VERBOSE)`, querying `pg_locks` and `pg_class` directly, printing identity hashes of injected beans — are cheap and available. Use them before writing a Javadoc, an ADR, or an assertion that depends on the answer. Distinct from M7's "verify packet claims against the code": these claims are unfalsifiable from our source and require probing the dependency itself.
- `[builder] [reviewer]` **Never assert an absolute value against state shared across test classes; diff a cumulative statistic, and scope every wait or poll to a specific identity.** Ten classes in this suite share one Spring context, and therefore one `MeterRegistry`, one database, and one live 30-second `HoldSweepService` — they carry an identical `@SpringBootTest @AutoConfigureMockMvc @Import(TestcontainersConfig.class) @ActiveProfiles("test") @TestPropertySource(...seed)` set, and Spring caches one context for the lot. Non-`@Transactional` siblings commit real multi-seat holds into that shared database, so a background tick can move a metric mid-assertion. Conversely, adding or removing any `@PropertyMapping` annotation such as `@AutoConfigureMockMvc` splits the cache key — and because Testcontainers containers are plain `@Bean`s with no reuse, a split context means a split *database* too. Neither sharing nor isolation is safe to assume in either direction: establish it (identity hashes of `ApplicationContext`/`MeterRegistry`, the live JDBC URL) before reasoning about cross-test interference. This is the third milestone running where shared test state contaminated or nearly contaminated an assertion — after M7's unscoped `pg_locks` poll and M8/T-001's need for PID-scoped polling — so treat cumulative-delta assertions and identity-scoped polling as the default, not the hardening step.
- `[planning] [builder] [reviewer] [docs]` **A fact worth stating twice will drift; when you correct one instance, grep for every other and fix them in the same change.** M8 hit this four times. A reasoning error about anonymous health visibility lived in ADR-0012, ADR-0013 *and* a task packet, and fixing the two ADRs still left the contradicting version sitting in an `application.properties` comment and in `loop/PLAN.md` — where it would have been re-read at the start of the next `/orchestrate` run and propagated onward. `README.md` claimed 117 tests against an actual 129. A "109 tests" baseline was stale by five commits, and `test-runner` rationalized the resulting mismatch as "+9, which aligns with the new test class" rather than flagging that it did not add up. Two consequences: after any correction, search the whole repo for the old claim before calling it done (historical `loop/STATE.md` entries are the deliberate exception — never rewrite those); and when an agent reports a number alongside a story about why the number is fine, verify the number, not the story.
- `[builder]` **Fix-first ordering matters most during revert-and-restore sequences, and the dangerous half-applied tree is the one that still passes.** An `implementer` was killed by a session limit immediately after announcing it would revert its instrumentation, having already reverted the tests and not yet restored them. That left production metrics in the tree with zero coverage — and crucially the suite still passed, so nothing signalled a problem and a commit there would have shipped an untested metric whose whole design turns on one branch. M7's lesson said work that lands fix-first survives an interruption; M8 adds the specific hazard and the specific remedy. Never hold tests reverted while their production code stands: restore them before doing anything else, including before writing up findings. When resuming an interrupted agent, require it to state its established findings *first*, before touching code, so a second interruption cannot lose them. And when any agent reports what it was about to do, read the tree rather than trusting the report.
- `[planning] [builder]` **When a verification is judged untestable, name the layer that judgement applies to and check whether another layer can reach it.** M8's grilling correctly concluded that "Postgres fatal to readiness" could not be proven from the test suite, because the Spring context cannot boot without a database — then stopped, and the task settled for asserting group *composition* with honest Javadoc about what that does not prove. The verification was in fact trivial one layer out: at the container level, `docker stop` on the database against a running app, which produced the real `healthy → unhealthy` transition and closed a second verification line that had been assigned to the user as manual. "Untestable" almost always means "untestable at the layer I was thinking about." Before accepting it, ask whether the container, the compose stack, or a live process can observe what an in-process test cannot.

## M9 retro (2026-08-17)
- `[planning]` **Verify framework internals during planning, not during implementation — the same class of claim costs a build failure at one stage and nothing at the other.** M9 ran the identical experiment twice with opposite results. T-001 discovered at build time that `Task#getRunnable()` wraps its target in a package-private `Task$OutcomeTrackingRunnable`, so a direct `instanceof ScheduledMethodRunnable` check never matches — two implementations compiled and failed before `javap -c` settled it. T-002 verified four equivalent claims (`PooledDataSourceConfiguration`'s `@ConditionalOnMissingBean({DataSource.class, XADataSource.class})`, the `dbHealthIndicator` backoff name, `AbstractHealthIndicator.health()` catching `Exception`, pgjdbc's integer-second timeout parsing) *during grilling*, landed them in the task packet as stated facts, and cost zero respins. M8's lesson said observe rather than assume; M9 adds where. When a packet's approach depends on how a framework behaves internally, decompile it while writing the packet — the answer becomes a constraint the builder designs around instead of a wall it hits. This is also what lets you pick an implementation *shape* that makes the guard observable: T-002's injectable seam existed specifically so a test could point one connection path at a dead port, which is what turned M8's "Postgres-down is untestable" into a passing in-process test.
- `[planning]` **A self-filed tech-debt issue's deliverables are a hypothesis, not a spec — re-derive its scope before planning from it.** Both of M9's source issues were materially wrong, and both were written by this same loop during M8's disclosure step, by agents with full context. #21 named two test Javadocs needing correction when there were four (it missed `HoldReleaseSeatLockRaceIntegrationTest`, which cites the ungated scheduler for the same reason as the two it did name). #20's named deliverable — set a global `spring.datasource.hikari.connection-timeout` — would have shortened the wait for *real user requests* on an application that blocks threads on `findByIdForUpdate` with no lock timeout, manufacturing exactly the spurious 500s `NoOversellIntegrationTest` and `BookingConfirmLoadIntegrationTest` exist to treat as defects. Both errors were caught only because planning re-read the code instead of transcribing the issue. Treat "Deliverables" as the reporter's best guess at the time; verify the count, and check whether the named fix has blast radius beyond its stated target, before a packet inherits it.
- `[planning] [reviewer] [docs]` **Mark the epistemic status of every number that reaches a durable document — "measured" and "estimated" must not read identically.** ADR-0014 stated a ~5s worst-case probe budget as settled fact, and that figure propagated into `PostgresReachabilityHealthIndicator`'s Javadoc and the `Dockerfile` HEALTHCHECK comment before review caught it. The `javap` check had only proved the three pgjdbc timeouts are integer-second-parsed — never how `connectTimeout`, `socketTimeout` and `loginTimeout` *compose* during a partial-blackhole connection, which is what the number actually claims. The failure mode is specific and nasty: a document that outlives the conversation that qualified it, read later as a verified constraint by someone tuning against it. This repo already separates observed from assumed everywhere else, so an ADR is the last place the distinction should blur. When a figure is derived rather than measured, say so in the same sentence and name what would settle it.
