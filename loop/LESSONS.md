# LESSONS — retro-earned constraints

Cumulative across milestones. Only `/retro` appends here; never reset.

## M6 retro (2026-08-13)
- When a milestone's task breakdown splits implementation from testing across separate tasks (e.g. T-004 owning tests for endpoints built in T-002/T-003), always tell `code-reviewer` this task-ownership split up front when spawning it for an implementation-only task. Without it, `code-reviewer` correctly notices a diff with new behavior and no tests, and — reasonably, given what it can see — flags it as a critical finding, which under `/orchestrate`'s rules escalates straight to `implementer` on a first pass. That happened on T-002: the finding was withdrawn on re-review once given the missing context, costing an extra review round for a non-defect. T-003 avoided it by including the context proactively. Fold this into every `code-reviewer` spawn for a milestone with a dedicated test task, not just remembered ad hoc per-task.

## M7 retro (2026-08-15)
- **Verify every factual claim in your task packet against the code before relying on it, and report discrepancies instead of working around them.** M7's packets were wrong four times: T-001 claimed a test shape exercised a Postgres lock-ordering path that Redis makes unreachable; T-004 claimed 21 error codes when there were 22 (the arithmetic omitted the code the task existed to add); T-006's exploit trace had a step the hold-row lock makes impossible; T-007 listed two lock-order offenders when there were three. Every one was caught by an agent that re-derived the claim — counting the enum itself, probing real Postgres — and every one would have shipped a wrong Javadoc, a wrong ADR, or an incomplete fix if taken on trust. Line numbers especially: they go stale the moment an earlier task edits the file.
- **A guard only counts if it can observe the failure it claims to catch — prove it by breaking the thing and watching the guard fire.** This failed three ways in M7. `SecurityConfig`'s Javadoc named "my bookings" as needing an auth carve-out and M6 shipped that exact endpoint without one, because a comment cannot fail a build. `OpenApiDocumentationTest` asserts response-status sets *exactly* so documentation drift fails loudly, yet missed T-008 entirely: the change moved the behaviour and touched neither the annotation nor the expectation, and an exact-match assertion is silent when both sides stay still. T-006's ownership guard was unreachable dead code until T-007's reordering made it live. By contrast, the two strongest deliverables of the milestone (T-006 and T-007) each ran their regression test against the *unfixed* code first and reported the failure output — do that whenever you add a guard.
- **Before writing a concurrency test, check that its parameters permit the outcome it asserts, and state in the Javadoc what it does not cover.** T-001's overlapping shape used 3-seat requests over a 5-seat pool, where any two requests must intersect, so only one thread could ever win — a costlier duplicate of the test beside it until the pool widened to 8. T-002's shared-hold race would have made `invocationCount() == 1` trivially true in a single pass, because only one thread ever receives a booking id; it needed two phases to become a real race. Assertions that cannot fail are worse than absent ones, because they read as coverage.
- **Judge locking by every row a transaction writes, not by where it calls `findByIdForUpdate`.** Both of M7's concurrency defects were invisible at the call site. In T-003 a plain `findAllById` pre-check loaded managed entities, so Hibernate's identity map served the later locked read from the pre-lock snapshot — the row lock was taken and its data ignored, and seats were genuinely double-booked. In T-007 nothing on the seats-first path asked for a hold lock at all; Hibernate took it when flushing a dirtied entity, producing an ABBA deadlock. See ADR-0010 and ADR-0011: before a locking loop the only safe reads of the type about to be locked are scalar projections and untouched lazy proxies, and lock order is about which table a transaction touches first by any means.
- **Sequence long tasks so the tree stays coherent at every step, and finish the fix and its regression test before the ADR or documentation.** Three agent runs in M7 were killed mid-task by API session limits and one stalled on a watchdog, twice leaving a task unverified. Work that lands fix-first survives an interruption; a half-applied refactor does not.
