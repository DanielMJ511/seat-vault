# A row lock is only as fresh as the persistence context: no unlocked entity read may precede it in the same transaction

Within a single transaction, an id that will later be read through `findByIdForUpdate` must not first be read into that transaction as a **managed entity** by any unlocked query. Hibernate's identity map returns the instance it already holds for a given id rather than refreshing it from the row the lock just protected, so `SELECT ... FOR UPDATE` genuinely takes the lock and the application then decides using the snapshot it read *before* it. ADR-0001 makes the Postgres row lock the concurrency authority; this rule is what stops the ORM from quietly reading around it. It is not an isolation-level problem — both bugs below reproduced at `READ COMMITTED` and would reproduce identically at `SERIALIZABLE`, because the stale value never came from the database on the second read at all.

The checkable form: **before a locking loop, the only reads of the to-be-locked type that are allowed are scalar projections and untouched lazy proxies.** A projection (`select es.id ...`, `select es.event.id ...`) puts nothing in the persistence context. Bulk `@Modifying` statements are also safe, since they materialize nothing.

A `@ManyToOne(fetch = LAZY)` association is safe *while it stays uninitialized* — `holdSeat.getEventSeat().getId()` is served from the proxy's identifier without a load, and the subsequent locked read is what supplies the state — but calling any other getter on that proxy before the loop initializes it and re-creates the defect exactly.

Four live call sites depend on this and are written the way they are on purpose. `HoldService#spansMultipleEvents` (via `EventSeatRepository#findDistinctEventIdsByIdIn`, not `findAllById`) and `HoldService#releaseHold` (via `EventSeatRepository#findIdsByCurrentHoldId`, not a `findByCurrentHoldId` returning entities) depend on the projection half; `BookingService#createFromHold` and `#releaseBookingSeats` depend on the lazy-proxy half. Simplifying any of the four back to the obvious entity query re-introduces a silent double-booking or hold-clobbering bug.

Both instances were real, not theoretical. The first double-booked seats under overlapping multi-seat hold requests (T-003, pinned by `HoldRedisUnavailableRaceIntegrationTest`); the second let `releaseHold` set a seat `AVAILABLE` and clear its hold pointer while another user's freshly-created hold owned it (T-006, pinned by `HoldReleaseSeatLockRaceIntegrationTest`).

`entityManager.clear()` before the loop fixes both and was used to confirm the diagnosis, but was rejected as the standing answer: it evicts everything, including rows the transaction locked deliberately (`releaseHold`'s `Hold` is locked and mutated across exactly that boundary), so it trades a lock bug for a reload bug. Per-seat `entityManager.refresh(...)` after each lock was rejected for the same reason it is easy to write and easy to forget — it leaves the dangerous query in place and adds a query per seat to compensate.

## Consequences

Projections are less convenient than entity queries, and each one costs a hand-written `@Query` plus a Javadoc explaining why it is not the obvious `findBy...` derived method. That friction is the point; the entity-returning spelling of both queries has been deleted rather than left in the repository as an attractive shortcut.

Mockito cannot catch a violation of this rule. `HoldServiceTest`'s release-race unit test stubs `findByIdForUpdate` to return a reassigned seat and passed throughout the T-006 defect's life — a mock has no identity map, so it asserts a behaviour the production code was structurally incapable of. Coverage for this class of bug has to be an integration test with a real session and two real transactions, which is why both regression tests are `@SpringBootTest` races against Testcontainers Postgres.

A caveat this ADR originally carried has since expired, and the way it expired is the point. It read: `releaseHold` also locks its `Hold` row for its whole transaction, which blocks every path that could re-home one of its seats (they all write that same `holds` row), so the T-006 clobber is not routinely reachable — and it warned that this was an accident of the current call graph rather than a guarantee, one lock in one method away from being false, leaving the ownership guard as dead code while it held.

It was false one task later. That hold-row lock was itself the ABBA deadlock ADR-0011 fixed, and fixing it meant moving the `holds` lock to *after* the seat locks. A competing `createHold` can now genuinely commit a re-homing while a release is parked on an earlier seat, so the guard is live code and the projection is what lets it see the change. Deleting the guard and re-running `HoldReleaseSeatLockRaceIntegrationTest` now fails with the seat clobbered back to `AVAILABLE`; before ADR-0011 it would not have. The discipline above, not any lock's incidental reach, is what this codebase relies on — and "currently masked" turned out to mean "masked for about a day."
