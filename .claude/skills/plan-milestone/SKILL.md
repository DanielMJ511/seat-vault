---
name: plan-milestone
description: Generate loop/PLAN.md and loop/tasks/ for SeatVault's next open GitHub milestone issue, grill the breakdown with the user via grill-with-docs, and record resulting decisions as ADRs before any code is written. Use when the user wants to start or re-plan a milestone, or says "/plan-milestone".
---

Run in the main session, never delegated to a subagent — the grilling step below is an interactive dialogue with the user that an isolated subagent cannot hold.

## 1. Resolve the current milestone

Run `gh issue list --label milestone --state open --json number,title,body,labels` and determine which single issue has no open blocking issue ahead of it (check native GitHub blocking dependencies, e.g. via `gh issue view <n>` and its "Blocked by" relationships, or `gh api` if the fields aren't in the list output). Exactly one issue should be unblocked and open.

If zero or more than one issue resolves as unblocked-and-open, stop and report the ambiguity to the user rather than guessing which milestone to plan.

## 2. Read the milestone issue

`gh issue view <n> --json number,title,body`. Parse the four fixed sections this repo's milestone issues always use: `## Goal`, `## Deliverables`, `## Verification`, `## Domain non-goals (CONTEXT.md)`.

## 3. Decompose into tasks

Read the relevant existing source files for the areas the Deliverables touch. Break the (prose, not checklist) Deliverables into concrete `T-00X` tasks — each task should be small enough for `builder` to complete and get reviewed in one pass, but large enough to be a coherent unit (e.g. "add BookingService.cancel with locking" is one task, not split further).

Overwrite `loop/PLAN.md` from scratch:

```
# PLAN — M<N>: <title> (issue #<n>)
Regenerated by /plan-milestone on <date>.

## Milestone summary
- Issue: #<n>
- Goal: <one line from the issue>
- Grilling ADRs: (filled in after step 4)

## Tasks
- [ ] T-001 — <title> (loop/tasks/T-001.md)
- [ ] T-002 — <title> (loop/tasks/T-002.md)
...

## Verification (from issue)
- [ ] <scenario 1 from the issue's Verification section>
...
```

Clear `loop/tasks/*.md` and write fresh packets, numbering from `T-001` (task numbering resets every milestone):

```
# T-00X — <title>
Milestone: M<N> (#<n>)   Status: pending

## Description
<what to build, derived from the Deliverables bullet(s) this task covers>

## Acceptance criteria
<derived from the Verification section, scoped to this task>

## Relevant conventions
<CLAUDE.md rules that apply, ADR numbers to read, CONTEXT.md terms in play>

## Files likely touched
<best guess from reading the existing code>

## Constraints from LESSONS.md
<carried in verbatim from loop/LESSONS.md at spawn time by /orchestrate — leave this section empty here>
```

## 4. Grill the breakdown before any code is written

Note the current highest ADR number in `docs/adr/` before starting (for later comparison).

`mattpocock-skills:grill-with-docs` has `disable-model-invocation: true` — it cannot be called via the Skill tool and must not be replicated by other means. Ask the user to run `/mattpocock-skills:grill-with-docs` themselves, presenting the drafted `loop/PLAN.md` and task packets as the plan to stress-test. This runs a `/grilling` session using `/domain-modeling` underneath — it will interrogate edge cases specific to this milestone, and — per `domain-modeling`'s own discipline — write any resulting ADR only when a decision is hard to reverse, surprising without context, and the result of a real trade-off; and update `CONTEXT.md` inline as domain terms get sharpened. When fact-finding is needed mid-grilling (not a decision, just information the codebase already has), dispatch an `Explore` agent to find it rather than asking the user — the grilling discipline reserves questions for the user's actual decisions. Do not duplicate the invoked skill's ADR-writing logic here — let it write ADRs in its own format.

Wait for the user to run the grilling session to completion (its own definition of done: the whole decision tree resolved, nothing silently assumed) before continuing.

## 5. Reconcile the plan with what grilling decided

If grilling changed scope (added an edge case that needs its own task, ruled out an approach a task packet assumed), update `loop/PLAN.md` and the affected `loop/tasks/T-00X.md` files accordingly.

Diff `docs/adr/` against the number noted in step 4 to find which ADR(s) grill-with-docs wrote. Fill in the "Grilling ADRs" line in `loop/PLAN.md`'s milestone summary with those numbers.

## 6. Log and stop

Append one entry to `loop/STATE.md`:

```
## <date> — M<N> milestone boundary
- Issue: #<n>
- Tasks planned: T-001..T-00N
- ADRs written: 00XX(, 00YY)
```

Stop. Do not write any application code. Tell the user to review `loop/PLAN.md` and the new ADR(s), then run `/orchestrate` when ready.
